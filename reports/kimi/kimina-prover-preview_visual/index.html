Kimina-Prover Preview：让大模型像人一样「思考」着写 Lean 4 证明

Kimina-Prover Preview: Towards Large Formal Reasoning Models with Reinforcement Learning

arXiv preprint · Technical Report 发表 2025.04 arXiv:2504.11354 Numina & Kimi Team 基座 Qwen2.5-72B

一句话：以往的神经定理证明器要靠外挂的树搜索算法（BFS / MCTS）在证明空间里硬搜，又慢又复杂，还基本不随模型变大而变强。本文换了个思路——用大规模强化学习，让一个 72B 大模型学会一种「形式推理范式」：在 <think> 里边用自然语言想、边写 Lean 4 代码片段，最后拼成完整证明。它把搜索内化进自己的推理，在 miniF2F 上拿到 80.7% (pass@8192) 的新 SOTA，并第一次展现出「越大越强」的规模效应。

本页基于已抓取的 arXiv 原文（2504.11354v1）正文、表格与全部原始图表构建。术语首次出现时给出英文原词，便于对照原文。

00 TL;DR · 30 秒抓住核心

  • 要解决的问题：形式化定理证明（在 Lean 4 里写出能被编译器验证的证明）需要严密、结构化、非线性的推理。过去的神经证明器要么靠外部搜索（开销大、不 scalable），要么用浅层 CoT，且不随模型规模变强。
  • 核心做法：把 Kimi k1.5 的 RL 推理流水线搬到形式数学，从 Qwen2.5-72B 出发做大规模 RL。设计一种 形式推理范式（formal reasoning pattern）——思维链里自然语言推理与 Lean 4 代码片段交替，最后组装成完整证明。奖励信号简单粗暴：Lean 编译器判对错（0/1）。
  • 关键配套：训练一个 Kimina-Autoformalizer 把自然语言题目自动翻译成 Lean 4 命题，攒出 20 万道形式问题；再用高效的 Lean Server（缓存 + 并行，10× 提速）做实时验证。
  • 结果：miniF2F-test 达 80.74% (pass@8192)，pass@1 就有 52.94%（样本效率极高）；首次出现随模型规模（1.5B→7B→72B）稳定提升的趋势；并涌现出探索多路径、反思修正、小例归纳等类人证明风格。
「与其外挂一个搜索算法去探索证明空间，不如让模型用自己的推理来隐式地搜索——由它自己决定『搜什么、怎么搜』。」
—— 释义自原文：Kimina-Prover implicitly flattens the step-wise search, allowing the model to decide both how and what to search.

01 问题：形式化定理证明，难在哪

先说清楚舞台：形式化定理证明是在 Lean 4 这样的交互式证明助手（proof assistant）里写证明。它的好处是每一步都能被编译器机械地验证——证出来就是真证出来了，没有「看起来对」的模糊地带。这也带来一个绝佳的训练信号：证明对不对，编译器说了算，天然适合强化学习。

但要让 LLM 把 Lean 4 证明写对，有几道坎绕不过去：

  • 推理是深层、结构化、非线性的：复杂证明往往要先想出一个证明草图、引入辅助引理、分情况讨论，再回头填坑。LLM 擅长「模式匹配 + 顺序生成」，但标准 SFT 或浅层思维链（CoT）不足以激发这种推理。
  • 依赖外部搜索，又慢又复杂：主流做法是让模型生成单步 tactic，再外挂 BFS / MCTS 去探索证明空间。搜索带来巨大的计算开销和系统复杂度，限制了规模化。
  • 不随模型变大而变强：以往专门为形式数学训练的神经证明器，几乎没有展现出「模型越大、性能越好」的规模效应——这说明它们没能把大模型的容量真正用在推理上。
  • informal 与 formal 之间有鸿沟：人类的非形式数学直觉（草稿纸上的推导）和严格的 Lean 4 代码之间缺乏对齐的训练数据，模型很难把「想法」翻译成「能编译的证明」。
本文要回答的问题
能不能不靠外部搜索，直接用大规模强化学习，把大模型的「长链推理」能力迁移到形式定理证明上？让模型像解 informal 数学题那样，在思维链里自己探索证明空间，并且越大越强？

02 已有方案卡在哪

本文没有罗列一长串 related work，而是聚焦几条与自己形成对比的技术路线。理解它们「卡在哪」，才能看懂 Kimina-Prover 为什么这么设计。点开每张卡片看具体做法与瓶颈：

🌳单步 tactic + 树搜索 主流路线
模型预测下一步 tactic，外挂 BFS / MCTS 在证明空间里系统搜索（如 DeepSeek-Prover、InternLM-StepProver、BFS-Prover）。
展开说明 ▸

做法：把证明看成一棵搜索树，模型在每个证明状态预测候选 tactic，由 Best-First Search 或 Monte Carlo Tree Search 根据启发式评分挑选、扩展最有希望的分支。

卡在哪：搜索组件是核心，但计算开销巨大（动辄上百万次采样）、系统复杂；价值/启发式难训。这条路受限于 scalability。

与本文关系：Kimina-Prover不外挂任何搜索，把「探索」内化进模型自己的思维链，pass@8192 即可超过它们的 pass@百万级。

📜整段证明生成 Whole-proof
给定证明状态，一次性生成整段 Lean 4 证明（如 DeepSeek-Prover-V1.5、Goedel-Prover）。
展开说明 ▸

做法：跳过逐步搜索，直接让模型从题面生成完整证明脚本，再交给 Lean 编译验证；失败就重采样。

卡在哪：缺乏深层、可解释的推理过程；模型只是「一口气写完」，难以在写之前规划证明草图，复杂题命中率低，需要海量采样。

与本文关系：Kimina-Prover 也是 whole-proof，但先在 <think> 里推理、规划再落笔，因此样本效率高得多。

🔗嵌入 informal 推理的尝试 Lean-STaR / MA-LoT
在预测 tactic 前先生成自然语言「想法」，或让 informal 推理与 Lean 验证交互。
展开说明 ▸

做法：Lean-STaR 在每步 tactic 前插入非形式思考；MA-LoT 用多智能体让自然语言推理与 Lean 4 验证结构化交互。

卡在哪：它们用的是较短的 CoT，或依赖从通用推理任务迁移 + SFT 得到的模型，而非直接用 RL 训练长链形式推理。深度不够。

与本文关系：本文指出「在形式证明里直接做 RL 驱动的长链推理」此前无人验证过可行性，Kimina-Prover 是第一次。

🧠通用推理大模型 o3 / Gemini 2.5
OpenAI o3-mini、Gemini 2.5 Pro 等通用推理模型，能解 informal 数学题。
展开说明 ▸

做法：靠大规模 RL 练出长链推理，在 AIME、IMO 等比赛上 informal 解题能力很强。

卡在哪：会解题却不会形式化。o3 倾向给出 informal、无法验证的答案；Gemini 有形式推理能力但常幻觉、生成无法编译的伪证明。在 miniF2F 上 pass@32 仅 24.6% / 37.7%。

与本文关系：这正是 informal-formal 鸿沟的直接证据——Kimina-Prover（68.85%）说明专门为形式推理做 RL 是必要的。

03 方法总览：三根支柱撑起一条 RL 闭环

Kimina-Prover 的训练配方（autoformalization + SFT + RL）可以拆成三根支柱，它们最终拧成一条强化学习闭环。先建立整体画面，后面几节再逐根展开。

① 自动形式化（Autoformalization）造题目
RL 需要海量、多样、可验证的形式问题，但人工写 Lean 4 命题太贵。于是训练一个 Kimina-Autoformalizer-7B，把自然语言数学题自动翻译成语法合法的 Lean 4 命题，配合人工标注，攒出 20 万道难度均衡的题库。
② 形式推理范式（Formal Reasoning Pattern）怎么想
设计一种结构化的思考格式：在 <think> 里让自然语言推理与 Lean 4 代码片段交替出现，强制思维块里的代码片段大部分要出现在最终证明里——以此对齐 informal 直觉与 formal 代码。再用 ~20K Claude 合成数据 + Kimi k1.5 的 informal 思考数据做冷启动 SFT。
③ 强化学习（Reinforcement Learning）练到强
从 Qwen2.5-72B 出发，沿用 Kimi k1.5 的 RL 流水线。每轮采样一批题、每题生成 8 个候选证明，交给 Lean 编译器验证，对就给 1、错给 0。再加上格式过滤、防崩溃技巧，迭代提升策略。还蒸馏出 1.5B / 7B 小模型并开源。
为什么这套组合能成
三根支柱缺一不可：没有题库，RL 无米下锅；没有推理范式，大模型的长链推理用不到形式证明上；没有 RL，模型只会模仿冷启动数据、无法自我超越。把它们接成闭环，模型就能在「自己造的题 + 编译器的对错反馈」里不断进化。

04 形式推理范式：边想边写代码，最后拼成证明

这是全文最核心的设计。难点在于：人类做数学是先在草稿纸上非形式地想思路，而 Lean 4 要求严格形式化的代码，两者之间缺乏对齐数据。Kimina-Prover 的解法是让模型在一个统一的思考格式里同时做两件事——把非形式直觉和形式代码逐块对齐。

图 1（原论文 Figure 2 左）：形式推理范式的输入输出结构——模型把证明拆成若干「非形式推理 + Lean 4 代码片段」的块，最后组装成完整证明。
展开说明 ▸
  • 输入（Input，上方蓝框）：每道题同时给出两种形式——自然语言题面（natural language problem statement）和形式化命题（formal language problem statement，即 Lean 4 的 theorem 声明）。两者并排，是「对齐 informal 与 formal」的起点。
  • 中间箭头：标注 Kimina-Prover，表示模型读入这对输入后开始生成。
  • 输出（Output，下方黄框）：不是一口气写完整证明，而是一连串 Reasoning Block。
  • 每个 Reasoning Block：内容是「非形式推理 + 一小段 Lean 4 代码片段」。模型先用自然语言想清楚这一步要干什么，再把它翻译成对应的 Lean 4 代码——这就是 informal↔formal 的逐块对齐。
  • Final Lean 4 Code（最底部红框）：把前面所有代码片段组装成一份完整、可编译的 Lean 4 证明。训练时强制要求：思维块里大部分代码片段必须真的出现在最终证明里，避免「想一套、写一套」。
  • 一句话总结：这个范式把「人类做数学的草稿过程」结构化进了思维链，让大模型的长链推理能力真正落到可验证的 Lean 代码上，同时让证明过程可读、可解释。

这个范式还有个副产品：可解释性。思维块把模型「内心戏」完整暴露出来，用户能看到它为什么这么证、卡在哪——这是搜索式证明器给不了的，也让它能当教学工具。论文给了一个完整的 running example，跟着走一遍就懂：

▸Running Example：等差数列求第 21 项（mathd_algebra_354）点开看模型完整的「想→写代码→拼证明」过程
① 输入：自然语言 + 形式命题
-- 已知等差数列第 7 项为 30、第 11 项为 60，求第 21 项。
theorem mathd_algebra_354 (a d : ℝ) (h₀ : a + 6 * d = 30) (h₁ : a + 10 * d = 60) :
    a + 20 * d = 135 := by
② 思维块 <think>：先用自然语言推导（节选）
<think>
通项 aₙ = a + (n−1)d。已知 a+6d=30、a+10d=60。
两式相减：4d = 30  ⟹  d = 15/2。
代回第一式：a + 6·(15/2) = 30  ⟹  a + 45 = 30  ⟹  a = −15。
于是 a + 20d = −15 + 20·(15/2) = −15 + 150 = 135。
现在把它形式化为 Lean 4：
③ 思维块里穿插的 Lean 4 代码片段
-- 先解出 d
have hd : d = 15 / 2 := by linarith
-- 再解出 a
have ha : a = -15 := by linarith [h₀, hd]
</think>
④ 最终组装出的完整 Lean 4 证明
theorem mathd_algebra_354 (a d : ℝ) (h₀ : a + 6 * d = 30) (h₁ : a + 10 * d = 60) :
    a + 20 * d = 135 := by
  have hd : d = 15 / 2 := by linarith
  have ha : a = -15 := by linarith [h₀, hd]
  linarith [ha, hd]

注意：思维块里出现的 have hd、have ha 等代码片段，原封不动地出现在最终证明里——这正是范式强制的 informal↔formal 对齐。

05 数据引擎：自动形式化造出 20 万道题

RL 是「在线」的——每一轮都要从题库里采题让模型练习。可形式问题极其稀缺，人工写 Lean 4 命题又慢又贵。于是本文专门训练了一个自动形式化模型 Kimina-Autoformalizer-7B，把自然语言题目翻译成 Lean 4 命题。这件事的难点是：没有现成的对错奖励——一个翻译出来的命题「忠不忠于原题」，编译通过并不代表语义正确。

STEP 1 · 初始化
SFT 学会 Lean 4 风格
以 Qwen2.5-Coder-7B 为底，用 PutnamBench、miniF2F、ProofNet、Compfiles 的形式命题做 SFT，学会写语法合法的竞赛级 Lean 4 命题（实验发现混入 Mathlib 风格数据反而有害）。
能写合法命题
STEP 2 · 专家迭代
编译 + LLM 评审双过滤
对候选翻译先用 Lean 4 过编译，再用 QwQ-32B 当裁判判断语义是否忠于原题（多次采样 + 一致投票降假阳性）。过两关的样本加入训练，迭代提升。
质量越滚越高
STEP 3 · 题库构建
20 万道难度均衡题
自动形式化产出 ~10 万 + 人工标注 ~1 万（重采样到 1:1），用 QwQ-32B 给难度评级、构造均衡分布，得到 20 万道题；并用否定证明、自适应剪枝持续净化。
RL 的弹药库
图 2（原论文 Figure 5）：Kimina-Autoformalizer 随专家迭代次数提升——一次性编译率升到约 90%，语义准确率升到约 66%。
展开说明 ▸
  • 横轴：专家迭代（expert iteration）的轮数，1 到 17 轮。
  • 纵轴：百分比（Percentage）。
  • 蓝线 Compilation Rate：生成的 Lean 4 命题一次性通过编译的比例，从约 66% 稳步升到约 90%——说明模型越来越会写合法语法。
  • 橙线 Accuracy：既能编译、又被 LLM 裁判判定语义忠于原题的比例，从约 37% 升到约 66%——这是更难的指标，因为它要求翻译「对得上意思」。
  • 读图重点：两条线都随迭代单调上升，且编译率始终高于准确率——印证了「能编译 ≠ 语义正确」，这也是为什么需要 LLM 裁判 + 人工监督这道额外关卡。
  • 一句话总结：专家迭代（生成→双过滤→回灌训练）是一个有效的自提升循环，把自动造题的质量从「勉强能用」滚到「可支撑大规模 RL」。
一个诚实的警告
论文特别指出：在这种没有硬性对错信号的任务上，模型会反复犯一些编译能过、但 LLM 裁判抓不到的错误，必须靠 Lean 专家持续监督。作者认为这揭示了「在不可验证领域应用 RL」的一大挑战。

06 强化学习：编译器当裁判，0/1 当奖励

冷启动 SFT 之后，真正让模型变强的是 RL。整条流水线是一个自我迭代的闭环：采题 → 生成证明 → Lean 编译验证 → 给奖励 → 更新策略。下面是原论文的流程图：

图 3（原论文 Figure 2 右）：形式 RL 流水线。左侧是数据源（题库 + 冷启动数据），中间是策略模型 Kimina-Prover，右侧是作为「环境」的 Lean Server，整体构成一条策略迭代闭环。
展开说明 ▸
  • Activation Data（左上）：20 万条「形式推理范式」示例，仅在初始化（mini-SFT）时用一次，给模型植入正确的思考格式——注意箭头标注 initialization only，它不参与后续 RL 循环。
  • Prompt Set（左下）→ Prompt Batch：题库含「自动形式化 10 万 + 人工标注 1 万×10」。每轮迭代采样 1000 道题（含 informal 与 formal 命题）组成一个 batch。
  • Kimina-Prover（Agent，中央）：策略模型本体。对采样到的题做 Roll-out，每题生成多个候选证明（Action Data：形式推理范式样本，规模约 8K × 32K tokens）。
  • Format Checking（中下菱形）：对每个候选做格式过滤。通过（Yes）才送去验证；不通过（No）直接丢弃（Discarded）——这是防止训练「格式崩溃」的关键闸门。
  • Lean Server（Environment，右）：作为强化学习的「环境」，用 Lean 编译器严格验证证明是否正确，并 Assign Reward（正确 1 / 错误 0）。
  • Roll-out Data（顶部）→ Policy Update：把带奖励、过滤后的 rollout 数据集回灌，执行策略更新，箭头指回 Kimina-Prover，完成一轮 RL Policy Iteration。
  • 一句话总结：整张图就是一条「题库采样 → 模型生成 → 格式过滤 → 编译器打分 → 回灌更新」的闭环，Lean 编译器提供了天然、不可作弊的奖励信号。

两个「防崩溃」细节，决定训练成败

形式 RL 的训练数据稀少、格式刚性，早期很容易出现 format collapse（格式崩溃）——负梯度把模型推向乱写。论文用两招稳住：

✓ 格式过滤 Format filtering
  • 每个样本至少一个 tactic 代码块
  • 代码块要覆盖最终证明 ≥ 60%，强制思维块与证明对齐
✓ 随机丢弃负梯度
  • 以概率 ω = 0.5 丢掉负梯度样本
  • 叠加 informal 数学数据混训，稳住训练、促进更复杂的推理

Lean Server：让验证不再是瓶颈

RL 每轮要验证成千上万个证明，验证速度直接决定能不能跑。本文用的 Numina Lean Server 基于官方 LeanREPL，靠两招提速：

  • LRU 缓存：按 import 头复用已加载好的环境，省掉重复加载 Mathlib 的巨大开销。
  • 多进程并行：同时管理多个 Lean REPL 进程，吃满多核 CPU。
  • 效果：验证吞吐 提速 10×，64 核机器上可达 100 次验证/秒；整个训练只需 640 个 CPU 核，而以往同类方法常要数千核。

蒸馏出小模型并开源

用训好的 72B 模型 rollout 数据，对 Qwen2.5-Math-1.5B / 7B 做 SFT，得到 Distill-1.5B 和 Distill-7B 两个开源小模型（cosine 学习率 2×10⁻⁵，3 个 epoch）。小模型也能继承不错的形式推理能力（见实验一节）。

07 有意思的点：会缩放，也会「像人一样想」

除了刷分，这套方法最有价值的几个发现，往往比 benchmark 数字更能说明它「为什么不一样」。

① 第一次：形式证明也「越大越强」

以往神经定理证明器有个尴尬：模型变大，性能却不怎么涨。Kimina-Prover 第一次打破了这一点。

图 4（原论文 Figure 3）：1.5B → 7B → 72B 三种规模下的 miniF2F 通过率。模型越大，各采样预算下的成绩都越高，且高预算下差距更明显。
展开说明 ▸
  • 横轴：模型规模，分 1.5B、7B、72B 三组。
  • 纵轴：miniF2F 通过率（Pass Rate %）。
  • 三种颜色柱子对应三种采样预算：浅米色 pass@1、深灰 pass@32、蓝色 pass@1024。
  • 趋势：同一预算下，柱子随模型变大单调升高。以 pass@1024 为例：1.5B 的 61.9% → 7B 的 70.0% → 72B 的 77.9%。
  • 关键细节：规模增益在高采样预算下更突出——72B 相对 7B 在三档预算上分别提升 +0.44%、+5.75%、+7.87%，说明大模型不只是「会算」，而是推理能力本身在随规模增长。
  • 一句话总结：这是第一个在形式数学上稳定体现 model scaling 的神经证明系统，意味着继续堆规模有望继续变强。

② 测试时缩放：学会「想得更久」

随着训练推进，模型自发学会用更长的思考去解更难的题——这是 reasoning model 的标志能力。

图 5（原论文 Figure 4）：训练迭代中，平均输出长度（橙）从约 2,500 涨到 10,000+ tokens，miniF2F pass@32 准确率（蓝）随之从约 61.8% 升到近 69%。
展开说明 ▸
  • 横轴：RL 训练迭代数（0 到 200）。
  • 左纵轴 / 蓝线：miniF2F 测试准确率（pass@32）。
  • 右纵轴 / 橙线：模型平均输出 token 长度（average token length）。
  • 橙线趋势：平稳上升，从约 2,500 token 涨到 10,000+——模型自发学会写更长、更完整的推理与证明。
  • 蓝线趋势：整体上升（约 61.8% → 近 69%），但明显比 informal 数学模型更「颠簸」，中段（50–150 迭代）常有跳变甚至回退。论文归因于：形式推理结构复杂、形式训练数据有限，模型在适应过程中不稳定。
  • 读图重点：两条线正相关——更长的思考换来更高的准确率，证明「测试时缩放」在形式证明里同样成立，只是过程更动荡。
  • 一句话总结：即便缺乏海量预训练语料，形式推理依然能靠 RL 实现 test-time scaling，这暗示该方法可迁移到其它「领域知识稀缺」的任务。

③ 涌现出类人的证明风格

初始化 + RL 之后，模型自发表现出一系列没有被显式编程的人类解题行为。点开卡片看原文给的真实案例：

🧭探索多条思路
面对难题会一口气尝试多种代换/技巧，失败后回溯，再锁定可行路径。
展开说明 ▸

案例（IMO 1983 P6 不等式）：模型先后尝试对称性、Ravi 代换、因式分解恒等式等多种思路，多次碰壁后回到最初的代换方法深入分析，最终发现可化为平方和（sum of squares）而证明完成。

意义：这是「试错—回溯—精炼」的人类式探索，搜索被内化进了思维链，而非外挂算法。

🔍小例归纳 + 反思修正
先算几个小例子找规律，提出猜想，再严格分情况证明。
展开说明 ▸

案例（数论 72826：大偶数拆成两奇数积之和）：模型先试算 n=40,42,44,… 找出规律，策略性地固定 a=3，再按 n mod 6 分三类构造、逐一严格证明。

意义：「观察小例 → 形成猜想 → 严格证明」是数学家最常用的套路，模型把它自发学了出来。

🧱用 have 分解，证明更可读
大量使用 have 把证明拆成命名小步，结构清晰，像人写的。
展开说明 ▸

对比 BFS-Prover：在同一道 IMO 1962 P2 上，Kimina-Prover 用一连串 have 语句把论证拆成有清晰目的的小步骤；而 BFS-Prover 靠逐步 tactic 搜索，很难从代码看出每步意图。

意义：体现了强大的证明草图规划能力，也让证明可读、可教学。

🌉有望弥合 informal–formal 鸿沟
学会在形式系统里推理后，反而获得更深的结构理解。
展开说明 ▸

通用模型（o3、Gemini）能 informal 解题却无法形式化；Kimina-Prover 证明了形式数学能力可以与非形式推理互补。作者推测：学会在形式系统里推理，能反过来增强 informal 数学能力——这是一个令人兴奋的未来方向。

但它也会犯错：不完整的分情况讨论

论文诚实地给了一个失败案例，比成绩单更能帮你判断它的边界。

▸失败案例：aime_1987_p5（incomplete case analysis）点开看模型在哪一步「想当然」了 
theorem aime_1987_p5 (x y : ℤ) (h₀ : y^2 + 3*(x^2*y^2) = 30*x^2 + 517) :
    3*(x^2*y^2) = 588 := by
  -- 模型想证明 x² ≤ 4，于是只检验了 x²=9、x²=16
  -- 发现它们让 y² 不是整数，就断定「只有 x² ≤ 4 可能」
  have h3 : x^2 ≤ 4 := by
    ...
    nlinarith [sq_nonneg (y:ℤ), h2]  -- 这一步并不能真正关掉目标

问题所在：模型只验证了 x=±3、x=±4 会让 y 非整数，就断言更大的 x 也不可能，却没有真正排除所有更大的情形。这种不完整的分情况讨论是它当前的典型失败模式之一。

▸成功案例：新证出一道此前无人解出的 IMO 题imo_1968_p5_1，点开看模型如何先立辅助引理再收尾

Kimina-Prover 证出了一道此前所有公开模型都没解出的题（imo_1968_p5_1）。它先陈述并花多行证明一个关键辅助引理 h2，再用 use 2*a 猜出正确答案，最后靠 h2 完成复杂推理链——展现出清晰的证明草图规划能力。

theorem imo_1968_p5_1 (a : ℝ) (f : ℝ → ℝ) (h₀ : 0 < a)
    (h₁ : ∀ x, f (x + a) = 1/2 + Real.sqrt (f x - f x ^ 2)) :
    ∃ b > 0, ∀ x, f (x + b) = f x := by
  have h2 : ∀ x, 0 ≤ f x ∧ f x ≤ 1 := by   -- 先立关键辅助引理
    intro x
    have h1 := h₁ (x - a)
    rw [show x - a + a = x by ring] at h1
    ...
  use 2 * a                                  -- 猜出周期 b = 2a
  constructor
  · linarith [h₀]
  · intro x
    ...                                      -- 用 h2 完成收尾

09 局限与未来方向

作者对边界和后续方向也很坦诚（这些往往比成绩单更能帮你判断它适不适合你的场景）：

  • 不完整的分情况讨论：典型失败模式——验证了几个小情形就「想当然」推广到所有情形（见上面 aime_1987_p5 案例）。
  • 测试时缩放过程颠簸：形式推理的准确率曲线不像 informal 数学那样平滑上升，中段常有跳变与回退，归因于形式训练数据有限。
  • 过度依赖高级 tactic：有时会滥用 nlinarith、norm_num 等强力自动化 tactic「暴力」收尾，未来计划过滤这类输出以提升证明质量。
  • 自动形式化的隐性错误：在缺乏硬奖励的自动形式化任务上，模型会犯编译能过、裁判抓不到的语义错误，需人工监督——这也是「不可验证领域 RL」的开放难题。

论文给出的后续方向包括：用 Lean 编译器反馈做迭代式纠错、接入外部工具（库检索、计算引擎）来缓解生成难题。

这篇报告最值得记住的一句话
当任务的对错能被编译器自动验证时，与其外挂一个搜索算法，不如用大规模 RL 让模型把搜索内化进自己的长链推理——这样不仅更省算力、样本效率更高，还第一次让形式证明随模型规模一起变强。
