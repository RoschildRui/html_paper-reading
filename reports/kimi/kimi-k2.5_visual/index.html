Kimi K2.5：把「会看图」和「会派活」装进一个万亿参数智能体

Kimi K2.5: Visual Agentic Intelligence

arXiv preprint · 2026.02 arXiv:2602.02276 Moonshot AI · Kimi Team 1.04T MoE / 32B 激活 开源权重（Modified MIT）

一句话：K2.5 在 Kimi K2 这个万亿参数文本基座上，额外灌入约 15T 图文混合 token，做了两件事——① 让文本与视觉联合优化、互相增强；② 引入 Agent Swarm（智能体集群），让一个可训练的「指挥官」把复杂任务拆成异构子任务、动态拉起最多约 100 个子智能体并行干活。结果：编码、视觉、推理、智能体任务全面 SOTA，长任务延迟最多降到原来的 1/4.5。

00 TL;DR · 30 秒抓住核心

  • 它是什么：一个原生多模态（native multimodal）的智能体模型——在 Kimi K2 文本基座上做持续预训练（continual pre-training），把视觉能力「长」进同一个模型，而不是外挂一个视觉模块。
  • 贡献一：文本×视觉联合优化。报告给出一串反直觉做法——早期、低比例地把视觉 token 混进训练（而非后期高比例外挂）；用 zero-vision SFT（只用纯文本 SFT）就能激活视觉工具使用；联合 RL 时视觉 RL 还反过来提升了文本成绩。
  • 贡献二：Agent Swarm + PARL。一个可训练的 orchestrator（指挥官）动态拆解任务、实例化一批冻结的子智能体（frozen subagents）并行执行；用 Parallel-Agent RL（PARL）训练，只更新指挥官、冻结子智能体，绕开「功劳分配」和「训练不稳」两大难题。
  • 效果：在广搜场景，Agent Swarm 把 BrowseComp 从 60.6% 提到 78.4%（超过 GPT-5.2 Pro 的 77.9%），同时延迟最多降低 4.5×。模型权重已开源。
「并行不是天生就更好——要不要、何时、怎样并行，全部交给环境反馈和 RL 探索去学。」
—— 释义自原文：parallelism is not presumed to be inherently advantageous; decisions … are explicitly learned through RL.

01 问题：通向「通用智能体」的两道坎

大模型正快速朝智能体智能（agentic intelligence）演进：能把复杂问题拆成多步计划，再交替「推理 + 调用工具」一步步执行。但报告点出两个绕不过去的瓶颈：

  • 多模态与文本「打架」：传统做法把视觉当成事后附加（post-hoc add-on）——在文本训练后期才大比例塞进视觉 token。结果常常是「视觉强了、语言弱了」，两种模态相互拖累，难以同时做好。
  • 串行执行 = 延迟爆炸：即便是能跑上百步的强智能体（如 Kimi K2-Thinking），工具调用也是一步接一步串行的，推理时间随步数线性增长。当任务变成「大规模检索 + 多分支推理」时，单个智能体的推理深度和工具预算会被迅速耗尽。
本报告要回答的问题
能不能让同一个模型既把文本和视觉一起练好（而非互相牺牲），又能在面对超复杂任务时自己学会并行——把「线性的步数」变成「并行的处理」？

02 已有方案卡在哪

报告没有罗列长篇 related work，而是把要对比的几条路线讲清楚，正好对应它自己的两个贡献。先建立画面感：

🧩视觉「后期外挂」 传统 VLM
在文本骨干训练的后期，才大比例（如 50%+）加入视觉 token，把多模态当作语言能力之上的补丁。
展开说明 ▸

做法：先把语言模型训得差不多，再在后期用高视觉比例做 continual training，快速「贴上」多模态能力。

卡在哪：把视觉视为 add-on 容易造成模态冲突——要么牺牲语言、要么牺牲视觉；而且视觉 SFT 数据稀缺、多样性差，常把视觉推理限制在简单图表和 crop/rotate/flip 这类原始操作。

与本文关系：K2.5 反其道而行——早期、低比例地全程混入视觉，并用 zero-vision SFT 绕开视觉数据稀缺问题。

⛓️串行单智能体 主流 agent
一个智能体把任务当成一条「推理→工具→推理」的长链，逐步执行。
展开说明 ▸

做法：单一上下文里串行地推理、调用工具，靠拉长步数（hundreds of steps）应对复杂任务。

卡在哪：推理时间随步数线性增长，延迟难以接受；单个上下文不断膨胀，最终耗尽推理深度与工具预算，复杂任务做不动。

与本文关系：Agent Swarm 把「一条长链」改成「多个并行短链」，用 critical steps（关键路径）而非总步数来衡量代价。

✂️被动式上下文管理 对比项
Hide-Tool-Result / Summary / Discard-all 等：等上下文撑爆了再去压缩或丢弃历史。
展开说明 ▸

做法：在推理时对上下文做事后截断——隐藏工具结果、摘要化、或干脆丢弃累积历史，以控制 token 用量。

卡在哪：这类方法本质是被动反应（reactive），常常牺牲结构信息或中间推理痕迹。

与本文关系：Agent Swarm 提供一种主动（proactive）的替代——把长任务拆成语义隔离的子任务，让上下文「分片（sharding）」而非「截断」。

03 贡献一：让文本与视觉「互相成就」

K2.5 的第一个核心论点是：文本与视觉的联合优化能同时增强两者、并避免冲突。这条主线由三个反直觉的发现 + 一个统一的视觉编码器架构支撑。

3.1 原生多模态预训练：早一点、淡一点，反而更好

核心设计问题：在固定的图文 token 预算下，什么样的「视觉注入时机 + 视觉比例」最优？传统智慧说「后期、高比例」。但 K2.5 的消融实验给出相反答案——早期融合（early fusion）+ 低视觉比例反而最好，且视觉比例对最终多模态表现影响很小。

  • 关键：即便是文本类能力（下排），低视觉比例同样不吃亏——说明「淡淡地、长期地」混入视觉，不会拖累语言能力。
  • 结论：视觉不该是「最后贴上去的补丁」，而应作为长期协同优化的一部分，从早期就低剂量参与。

一句话总结：与其后期猛灌视觉，不如早期细水长流——多模态表征在长期共训中更均衡。

3.2 Zero-Vision SFT：只用「纯文本」就能点亮视觉工具

预训练后的视觉模型并不会自动「看图用工具」，这给多模态 RL 出了个冷启动（cold-start）难题。传统解法是人工标注视觉 CoT 数据，但这类数据少、多样性差。K2.5 的妙招是 zero-vision SFT：

  • 只用纯文本 SFT 数据来激活视觉、智能体能力——因为高质量文本 SFT 数据「又多又杂」。
  • 所有图像操作都用 IPython 里的程序化操作来代理（proxy），相当于把传统「视觉工具使用」一般化：用代码做二值化数物体、估算尺寸、定位、计数、OCR……
  • 反直觉的发现：在这一步加入人工设计的视觉轨迹，反而损害泛化；纯文本 SFT 表现更好——因为联合预训练已经建立了强视觉-文本对齐，能力能自然跨模态迁移。

3.3 联合多模态 RL：视觉 RL 竟然反哺了文本

zero-vision SFT 之后，再用结果奖励（outcome-based RL）在「必须看图才能答对」的任务上精炼：视觉定位与计数、图表/文档理解、视觉关键的 STEM 题。随训练投入（RL FLOPs）增加，视觉能力持续提升（见下图）。

  • 关键信息：起点（zero-vision SFT）几乎没用任何视觉 SFT 数据，却足以让长程视觉 RL「接得住」——证明纯文本激活 + 长程视觉 RL 这条组合拳成立。

一句话总结：视觉能力不是靠堆视觉 SFT 数据「教」出来的，而是靠纯文本激活 + 长程 RL「练」出来的。

双向增强：text bootstraps vision，vision refines text
正是基于「视觉能力能从 zero-vision SFT + 视觉 RL 中涌现，又能反哺文本」这一发现，K2.5 在后训练里干脆采用联合多模态 RL：RL 域不再按「输入模态」划分，而是按能力（知识 / 推理 / 编码 / 智能体……）划分，让纯文本与多模态 query 一起训，最大化跨模态能力迁移。

04 贡献二：Agent Swarm —— 让模型自己学会「派活并行」

这是报告的招牌。与其把任务当成一条推理长链，K2.5 通过动态任务拆解 + 子智能体实例化 + 并行子任务调度发起一个「智能体集群」。下面这张架构图是全节最重要的图：

图 3（原论文 Figure 3）：一个可训练的 Orchestrator（指挥官）动态创建一批专业化的冻结子智能体，把复杂任务拆成可并行的子任务，分布式执行后汇总成最终结果。
展开说明 ▸
  • 最左侧蓝色长条 = Orchestrator（指挥官）：唯一可训练的部分。它持有一组工具：create_subagent（创建子智能体）、assign_task（派发任务）、search、browser 等。
  • 第一步「create subagents」：指挥官根据任务，动态实例化一批异构子智能体——图中有 AI Researcher、Physics Researcher、Life Sciences Researcher、Anthropology Researcher、Fact Checker、Web Developer……每个都带自己的工具集（放大镜=搜索、Python=代码、窗口=浏览）。返回 success。
  • 第二步「Assign Tasks」（上方大块）：指挥官把任务批量分派——例如 AI Researcher 同时领 Task 1~4，Life Sciences Researcher 领 Task 96~99……图中一直排到 Task 100，对应「最多约 100 个子任务并行」。各子智能体跑完把 task N result 回传给指挥官（左侧一列箭头）。
  • 第三步（下方块）= 又一轮 Assign Tasks：拿到第一批结果后，指挥官可以再起新一批角色（Fact Checker 核查、File Downloader 下载、Web Developer 开发），说明拆解是分阶段、动态的，而非一次性静态划分。
  • 最底部「Final Results」：指挥官聚合所有子智能体的产出，合成最终答案（必要时还能临时 spawn 验证者 verifier）。
  • 关键设计：子智能体是冻结的（frozen）中间 checkpoint，它们的执行轨迹被当作「环境观测」、不参与梯度更新；只有指挥官被 RL 训练。这把「高层协调逻辑」与「底层执行能力」解耦。

一句话总结：指挥官学会「创建谁、派什么、何时并行、如何汇总」，子智能体只管埋头执行——分工明确，所以好训。

PARL：为什么「冻结子智能体、只训指挥官」

训练这套并行编排用的是 Parallel-Agent Reinforcement Learning（PARL）。它刻意采用解耦架构：可训练的指挥官 + 从固定中间 checkpoint 实例化的冻结子智能体。这样设计是为了绕开端到端协同优化的两个老大难：

  • 功劳分配模糊（credit assignment ambiguity）：多智能体下，结果奖励既稀疏又嘈杂——最终答对不代表每个子智能体都执行完美，答错也不代表全员有错。把子智能体冻结、当作「环境观测」，就不必为它们的每一步分配梯度。
  • 训练不稳定（training instability）：解耦「高层协调」与「底层执行」后，收敛更稳。工程上还先用小号子智能体训指挥官，再切到大模型；并能动态调节子智能体与指挥官的推理实例配比，榨干集群资源。

PARL 奖励：一个主奖励 + 两个「纠偏」奖励

并行编排的反馈是延迟、稀疏、非平稳的，所以奖励要专门设计来对抗两种退化行为：

rPARL(x,y) = λ₁·rparallel + λ₂·rfinish + rperf(x,y)
λ₁、λ₂ 是辅助奖励的权重，训练中逐步退火到 0，确保最终只为主目标（任务表现）优化。
rperf · 任务表现
主奖励：评估最终解 y 对任务 x 的整体成功与质量。这是真正想优化的目标。
+
rparallel · 鼓励并行
对抗串行坍缩（serial collapse）——指挥官偷懒退化成单智能体。靠奖励「实例化子智能体」逼它去探索并行调度空间。
+
rfinish · 鼓励完成
对抗虚假并行（spurious parallelism）——为刷并行指标乱开一堆没用的子智能体。靠奖励「子任务真正完成」逼它做有效拆解。

关键步数（Critical Steps）：用「关键路径」衡量真实耗时

并行场景下，「总步数」不再等于「耗时」。报告类比计算图的关键路径（critical path），定义关键步数——每个阶段的耗时由该阶段跑得最久的那个子智能体决定：

CriticalSteps = Σt=1..T ( Smain(t) + maxi Ssub,i(t) )
每个阶段 t 的代价 = 主智能体步数 + 该阶段并行组里最长子智能体的步数。多开但不缩短最长分支 = 没收益。

用关键步数（而非总步数）来约束训练与评测，直接激励有效并行：只有把活均衡地铺开、缩短最长分支，才能降低端到端延迟；盲目堆并发或堆总工作量都没用。

训练信号：并行度是「学」出来的

展开说明 ▸
  • 左图 Training Accuracy vs Steps：横轴是 RL 训练算力，纵轴是训练准确率。蓝点是实测、红线是平滑曲线，从约 37% 平稳爬升到约 64%。

  • 两图对照：准确率和并行度同步上升，说明并行不是被硬塞的——而是指挥官发现「并行确实能把任务做得更好更快」后，主动学来的策略。
  • 呼应奖励设计：rparallel 把它从串行坍缩里拽出来、rfinish 防止它乱开子智能体，二者合力才有这条平滑上升的并行度曲线。

一句话总结：并行度曲线是「指挥官学会派活」的最直接证据——它越训越愿意、也越会并行。

子智能体并非提前定义好，而是指挥官根据 query 动态实例化——它会推断「需要几个、什么时候要、什么专长」。于是一个异构的智能体群会自然涌现：

  • 高频角色：Biography Researcher、Verification Specialist、Cross Reference Analyst、University Researcher、Article Researcher、Timeline Researcher 等——大量是「研究 + 核查 + 交叉验证」类。

05 训练全景：从 K2 基座到 K2.5

上面两个贡献都建立在一套完整的训练流程上。这里轻量过一遍「基座 → 预训练 → 后训练 → 基建」，不必逐一深究，知道每块在做什么即可。

基座与预训练三阶段

K2.5 的地基是 Kimi K2：万亿参数 MoE（1.04T 总参 / 32B 激活，384 专家选 8，MuonClip + QK-Clip 稳训），在 15T 文本 token 上预训练。在此之上，K2.5 用约 15T 图文混合 token 走三个预训练阶段：

STAGE 1 · ViT
视觉编码器预训练
从 SigLIP 继续训 MoonViT-3D，只用 caption 交叉熵（不含对比损失），对齐图/视频与语言。~1T token，序列长 4096。
建立原生分辨率视觉编码器
STAGE 2 · 联合
图文联合预训练
从近末期的 K2 checkpoint 继续，同时训 ViT 与 LLM，加大编码相关数据权重，控制每个数据源的最大 epoch。~15T token，序列长 4096。
语言与多模态同步增强
STAGE 3 · 长上下文
长上下文 mid-training
混入高质量数据 + 长文本/长视频，用 YaRN 逐步把上下文从 32K 扩到 262K。500B→200B token。
长文档与长视频理解

后训练：SFT + RL

  • SFT：沿用 K2 流程，用 K2、K2-Thinking 和一批内部专家模型合成高质量候选回复，按领域定制管线、结合人工标注与多阶段验证，强调「交互式推理 + 精准工具调用」。
  • RL（统一智能体 RL 环境）：策略优化用带 token 级裁剪（token-level clipping）的目标——只看 log-ratio 把「离策略漂移」框住（不论优势正负），对长程多步工具使用的稳定性至关重要；优化器仍是 MuonClip。
  • 奖励组合：可验证任务用规则奖励；通用任务用生成式奖励模型（GRM）捕捉「有用性、相关性、详略得当、美感、严格遵循指令」等细粒度偏好；视觉任务设计专门奖励（IoU 软匹配、归一化编辑距离、计数差等）。

Toggle：在「想得够」和「说得省」之间来回切

测试时扩展（test-time scaling）拿算力换推理质量，但死扣预算会导致「长度过拟合」——模型学会截断推理，反而用不上更多算力。Toggle 是个交替训练启发式：每 m 轮在两个相位间切换——Phase 0 限预算（仅当该题平均正确率超阈值 λ 才施加，避免过早牺牲质量）与 Phase 1 放开扩展（鼓励用满算力）。

图 5（原论文 Figure 5）：在 K2 Thinking 上应用 Toggle 后，性能几乎不变（左），但输出 token 大幅下降（右）——平均省 25%~30%。
展开说明 ▸
  • 左雷达图 = 性能（%）：灰色 = Toggle 前，蓝色 = Toggle 后。各轴是 HMMT、GPQA Diamond、AIME2025、Overall、LiveCodeBenchV6、MMLUPro 等基准。绿标=提升、红标=下降，统计为「改善 5 项 / 退化 2 项」，且变动都很小（多在 ±2% 内）。
  • 右雷达图 = token 用量：橙色 = Toggle 后。每个轴上的绿标显示减少的 token 数（如 -7967、-8127、-6179），统计为「减少 7 项 / 增加 0 项」。
  • 对照两图：左边几乎不动、右边大幅缩小——说明 Toggle 把 CoT 里重复验证、机械计算这类冗余砍掉了，而没有牺牲答对率。
  • 泛化：即使只在数学和编程上训练，模型在 GPQA、MMLU-Pro 上也能稳定省 token，几乎不掉点。

一句话总结：Toggle 让模型「该长则长、能短则短」，省下两三成 token 还几乎不掉分。

基建一笔带过：DEP（Decoupled Encoder Process）
多模态训练里，视觉编码器和文本嵌入挤在流水线第一级（Stage-0），因图像数量/分辨率波动造成负载与显存剧烈抖动。DEP 把视觉编码器复制到所有 GPU，按负载均衡地先跑「视觉前向」，丢弃中间激活只留输出，再像纯文本一样高效训练主干，最后重算视觉反向。结果：多模态训练效率达到纯文本的 90%，且能直接复用 K2 的并行策略。

06 有意思的点

除了主线，有几处取舍与发现值得单独拎出来——它们往往比 benchmark 数字更能帮你判断这套方法适不适合自己的场景。

🔄早期低比例融合反直觉地更好
固定预算下，「早期、淡淡地」混视觉胜过「后期、猛灌」视觉。
展开说明 ▸

传统智慧认为多模态是语言之上的 add-on，应后期高比例注入。K2.5 的消融却显示视觉比例对最终表现影响很小，而早期低比例反而最优。

启发：把视觉当作长期协同优化的一等公民，而非临门一脚的补丁。

🚫加人工视觉轨迹反而有害
激活视觉能力时，纯文本 SFT 胜过「文本+视觉」SFT。
展开说明 ▸

因为联合预训练已建立强视觉-文本对齐，能力能自然跨模态迁移；此时再塞入多样性差的人工视觉轨迹，反而损害泛化。

边界：这条结论依赖「预训练阶段已做好图文对齐」——否则纯文本激活未必接得住。

↔️视觉 RL 反哺文本
做完视觉 RL，纯文本基准不降反升（MMLU-Pro/GPQA/LongBench 均 +1.7~+2.2）。
展开说明 ▸

分析认为视觉 RL 改善了「结构化信息抽取」类问题的校准，降低了「类视觉」查询上的不确定性，从而跨模态泛化到文本推理。

言下之意：模态之间不是零和——对齐做得好，一种模态的进步能外溢到另一种。

🧊冻结子智能体 = 干净的功劳分配
只训指挥官、冻结子智能体，把多智能体 RL 的两大难题一并绕开。
展开说明 ▸

子智能体输出被当作「环境观测」、不参与梯度，从而避免功劳分配模糊与训练不稳。两个辅助奖励（rparallel/rfinish）再分别防住串行坍缩与虚假并行。

价值：这是一种很务实的「先把能训稳的部分训稳」的工程哲学。

⏱️用「关键路径」而非「总步数」
Critical Steps 让「多开但不缩短最长分支」毫无收益。
展开说明 ▸

把每阶段代价定义为「主步数 + 最长子智能体步数」，奖励信号天然偏向均衡拆解，而非盲目堆并发或堆总工作量。

启发：评测并行系统时，指标选错（总步数）会把模型带偏。

📐Toggle 治「长度过拟合」
在限预算与放开扩展之间交替，省 25~30% token 还几乎不掉分。
展开说明 ▸

死扣预算会让模型学会截断推理、用不上更多算力（length-overfitting）。Toggle 用交替优化把「会推理」和「会省」两个目标调和起来。

边界：限预算只在「该题平均正确率超阈值」时才施加，避免过早牺牲质量。

08 怎么看这套方法 · 结论

报告的结论很克制：可扩展、通用的智能体智能，可以靠「文本×视觉联合优化 + 并行智能体执行」来实现。这套思路的适用边界值得留意：

  • Agent Swarm 的甜区是「可并行」的任务：广搜、批量下载、超大规模文档阅读、长文写作——能被拆成相互独立子任务的场景收益最大；强串行依赖的任务并行不一定划算。
  • 子智能体是冻结的：当前只训指挥官。报告也指出，端到端协同训练（同时优化子智能体）仍是开放方向——现在是用「可训稳」换「上限」。
  • 评测口径需对齐：不少对比是内部复测（带 *），部分场景（如 BrowseComp）依赖特定上下文管理策略；跨报告比较时要看清设置。
  • 视觉激活依赖强预训练对齐：zero-vision SFT「纯文本激活视觉」之所以成立，前提是联合预训练已建立强图文对齐——这套配方不一定能直接照搬到对齐较弱的模型上。
这份报告最值得记住的一句话
与其预设「并行更好」或「视觉是附加」，不如把这些决策交给环境反馈和 RL 去学——让模型自己决定何时看图、何时派活、何时并行。K2.5 用一条上升的并行度曲线和一张更快更准的成绩单，说明了这条路走得通。
