Kimina Lean Server：为大规模形式化验证而生的高性能 Lean 服务器

Kimina Lean Server: A High-Performance Lean Server for Large-Scale Verification

arXiv preprint · Technical Report 发表 2025.04 arXiv:2504.21230 Project Numina · Cambridge · Moonshot AI 开源 · MATH-AI Workshop

一句话：用 Lean 形式化证明给定理证明模型做强化学习，瓶颈不在模型而在「验证」——每条候选证明都要重新加载庞大的 Mathlib 库再编译，慢且不可扩展。本文用服务端并行（一核一个 Lean REPL）+ LRU import 缓存（复用已加载好库的 worker）把验证吞吐拉到比次优工具快 1.5–2×，并配一个「一个 check 函数搞定」的轻量 Python 客户端，已支撑 Kimina-Prover 两度登顶 miniF2F。

本页基于已抓取的 arXiv HTML 原文（v3）正文、表格与官方架构图构建。术语首次出现时给出英文原词，便于对照原文。

00 TL;DR · 30 秒抓住核心

  • 要解决的问题：定理证明模型（如 Kimina-Prover）的 RL 训练，需要把 Lean 编译结果当作奖励信号。这意味着每一步都要大批量、高速地验证海量候选证明，而已有 Lean 工具在这里成了吞吐瓶颈。
  • 两个核心机制：① 服务端并行——维护一池 Lean REPL 进程，一个核心跑一个常驻 REPL，把多核 CPU 吃满；② LRU import 缓存——把脚本拆成 header（import）+ body，用 header 当 key 复用「已经加载好 Mathlib」的 worker，省掉最贵的初始化。
  • 好用的客户端：一个 PyPI 包，单个 check() 调用提交一批证明、拿回结构化反馈（报错、环境 id、耗时、可选 infotree），并行与缓存全在服务端透明完成。
  • 额外能力：处理 Lean 的 infotree，把证明切成互不重叠的 tactic + tactic state 序列，专为树搜索（tree search）模型提供训练数据。

01 问题：RL 训练定理证明，卡在「验证」这一环

近两年的形式化数学 AI（neural theorem proving）有一条清晰的主线：把大语言模型接到 Lean 4 这样的交互式证明助手上，用「证明对不对」作为强化学习的奖励信号来训练模型。Kimina-Prover、DeepSeek-Prover-v2、Seed-Prover 等 SOTA 工作都走这条路。

但这条路有一个容易被忽视的工程现实：RL 每一步都会产生成千上万条候选证明，全部要送进 Lean 编译验证。验证一旦慢，整条训练流水线就被拖住。而验证之所以慢、之所以难扩展，根子在两处：

  • 初始化代价极高：启动一个 Lean REPL，最贵的部分是加载 Mathlib 这种大型库。如果每验证一条证明都重新起一个 REPL、重新 import 一遍，绝大部分时间都耗在「热身」上。
  • 难以并行：单个 Lean REPL 进程是单线程，一个进程吃不满多核 CPU。多数已有工具没有为「跨核并行」设计，硬件再强也用不上。
本文要回答的问题
能不能做一个专为大规模 RL 流水线设计的 Lean 服务器，既把多核 CPU 吃满，又避免反复加载大型库，还顺手把「从 Python 调 Lean、拿结构化反馈、提取证明数据」这件麻烦事变简单？

02 已有方案卡在哪

社区已有不少把 Lean 4 接到 Python 的工具，各有取舍。把它们按「能不能并行、能不能缓存 import、能不能提取数据、适不适合大规模 RL」摆在一起，就能看清 Kimina Lean Server 想补的那块空白：

工具跨核并行import 缓存证明数据提取大规模 RL 验证
LeanREPL（官方）✕ 单线程✕部分✕
Pantograph✕ 单线程✕✓ 强✕
leanclient✓（LSP）✕✕有限
LeanInteract✓（多 REPL）✕✕有限

展开看每个工具具体怎么做、卡在哪——尤其是为什么「能并行」也不等于「适合大规模 RL」：

⚙️LeanREPL（官方）底层接口
把 Lean 暴露成一个交互式子进程，可逐条发 tactic 拿新 goal，或整段证明拿最终结果。
展开说明 ▸

做法：read-eval-print loop（读取-求值-打印循环），是 Lean 官方提供的最底层 Python 交互入口，其它工具大多构建在它之上。

卡在哪：原生不支持多行 have/let 写法、calc 模式、conv 模式；而且本质单线程，吃不满多核，不为高吞吐设计。

与本文关系：Kimina 服务器直接构建在官方 LeanREPL 之上，因此天然兼容 REPL 支持的任何 Lean 版本——把它的单线程包成多进程池。

🧩Pantograph 功能丰富
LeanREPL 的增强替代品，把子目标（subgoal）当独立对象处理。
展开说明 ▸

做法：独立处理 subgoal，支持 have/let/conv/calc，能提取 tactic state 和带注释的完整证明脚本，弥补了 LeanREPL 的表达力短板。

卡在哪：和 LeanREPL 一样仍是单线程，没有为大规模 RL 的高吞吐验证设计。

与本文关系：Kimina 在客户端用 infotree 处理补上了 calc/conv/have/let 这些「难提取」的 tactic（见后文），同时保留并行能力。

🔀leanclient 支持并行
通过 Lean 的语言服务器协议（LSP）与 Lean 交互，支持文件级并行批处理。
展开说明 ▸

做法：走 LSP（Language Server Protocol）通道，能并行批量处理多个文件。

卡在哪：并行能力有了，但大规模训练下性能仍受限，且不做证明数据提取（拿不到单步 tactic 与 tactic state）。

与本文关系：本文的主要性能对比基线之一。Kimina 在 8/16/32/64 核全面更快。

🔁LeanInteract 支持并行
通过管理多个 REPL 实例来获得类似的并行能力。
展开说明 ▸

做法：用 LeanREPLConfig + 多个 AutoLeanServer 实例（官方推荐：每进程一个）来并行跑证明。

卡在哪：每条证明各自一个 server，没有 import 复用/缓存；要管理可复用的实例池，正是本文付出的工程量。性能仍受限，也不做数据提取。

与本文关系：本文另一个主要基线，也是说明「缓存」价值的反例。

🏋️LeanDojo / ProofWala gym 环境
提供更完整的、类似 gym 的环境，面向数据提取与证明搜索。
展开说明 ▸

做法：构建交互式「健身房」环境，便于做 proof search 与提取训练数据，功能全面。

卡在哪：没有为现代 RL 工作流所需的验证速度做优化——能提数据，但验证吞吐跟不上大规模训练。

与本文关系：本文要在「数据提取能力」之外，额外把验证速度做到适合 RL 的量级。

🎯共同空白 本文切入点
能并行的不缓存、能提数据的不够快——没有一个同时把四件事做好。
展开说明 ▸

已有工具要么并行但不缓存 import（leanclient/LeanInteract），要么能提数据但太慢（LeanDojo/ProofWala），要么单线程（LeanREPL/Pantograph）。

本文切入点：把「并行 + import 缓存 + 数据提取 + 轻量客户端」一次性整合到一个为大规模 RL 专门工程化的服务器里。

04 架构：并行 + 缓存怎么协同调度

这张官方架构图是全文的核心。它回答一个具体问题：一条带 Lean 代码的请求进来后，服务器按什么优先级把它派给某个 Lean REPL？ 关键就在「能不能复用一个已经加载好同样 import 的 worker」。

图 1（原论文 Figure 1）：Kimina Lean Server 的并行与缓存架构。请求经 Splitter 拆成 header H / body B，再沿一条四级优先级决策链派发，核心目标是尽量命中「已加载好 import」的 REPL。
展开说明 ▸
  • 最左 · 请求入口：客户端提交一批含 Lean 4 代码片段（snippets）的 API 请求。
  • Splitter（拆分器）：把每段脚本拆成两部分——Header H（只含 import 等声明）和 Body B（其余的定理与证明代码）。H 就是后面缓存用的「钥匙」。
  • 判断① 有没有「带 header H 的空闲 REPL」？ → Yes：直接 Run body B。这是缓存命中的最快路径：worker 已经加载好这套 import，省掉最贵的初始化，只需编译 body。
  • 判断② 有没有空闲核心（free core）？ → Yes：新建一个加载 header H 的 REPL，再跑 body B。虽然要付一次 import 代价，但用上了一个原本闲置的核。
  • 判断③ 有没有任意空闲 REPL？ → Yes：销毁一个（最久未用的）空闲 REPL，腾出核心，新建加载 H 的 REPL 再跑 B。这就是 LRU 驱逐：当核心被别的 header 占满时，淘汰最没用的缓存换进新 header。
  • 判断④ 都没有？ → Wait a bit…（稍等片刻），然后回到判断①重试（图底部的回环箭头）。所有核心都在忙时短暂排队，避免过载。
  • 配色含义：绿色高亮 idle REPL 与 header/body 这些关键对象，紫色高亮 free core；箭头表示请求依次流过这四级判断。

一句话总结：调度按「复用命中 > 用空核新建 > LRU 驱逐后新建 > 等待」的优先级派发——既尽量吃满多核，又尽量复用昂贵的 import 缓存。

为什么「一核一 REPL」很关键
单个 Lean REPL 进程是单线程，CPU 占用不超过一个核。所以服务器给每个核常驻一个 REPL 进程——既不让进程互相抢核（关掉超线程 SMT 进一步保证稳定），又能让总吞吐随核心数近线性增长。

05 客户端：一个 check() 提交，一棵 infotree 提数据

服务端再快，调用麻烦也没人用。Kimina 的客户端是一个 PyPI 包，把 REST API 包成最简单的形式：所有交互都通过一个 check() 调用——传入一批 Lean 脚本，返回一批结果，并行执行与 REPL 缓存全在服务端幕后完成。

每条结果里包含：Lean 的告警/报错信息、REPL 环境标识、耗时、以及一个可选的 infotree。下面是最小用法：

📦 最小用法：提交一批证明并拿回结果
# 高层接口：一行跑完一个 benchmark（自动加载/处理数据）
from kimina_client import KiminaClient

client = KiminaClient()
client.run_benchmark(
    dataset_name="AI-MO/NuminaMath-LEAN",
    n=1000, batch_size=8, max_workers=10,
)
▸更可控的写法：手动构造 Snippet 调用 check()点开看如何逐条提交并读取每条的验证状态 
from datasets import load_dataset
from kimina_client import KiminaClient
from kimina_client.models import Snippet

dataset = load_dataset("AI-MO/NuminaMath-LEAN", split="train")
dataset = dataset.filter(lambda x: x["ground_truth_type"] == "complete")
dataset = dataset.select(range(1000))

client = KiminaClient()
snippets = [
    Snippet(id=str(dataset[i]["uuid"]),
            code=dataset[i]["formal_ground_truth"])
    for i in range(len(dataset))
]

# 一个 check 调用，服务端并行 + 缓存全透明
resp = client.check(snippets, timeout=120)
for r in resp.results:
    print(r.id, r.analyze().status.value)

infotree → 干净的「tactic + tactic state」序列

训练树搜索（tree search）模型需要把一条证明拆成一步步的 tactic，并记录每步执行前后的目标状态（goals）。Lean 的 infotree 信息丰富但原始、且不同 tactic 的区间会互相重叠。客户端用一条小流水线把它清洗成规整序列：

STEP 1
提取位置
从 infotree 里定位每个 tactic 的位置（起止偏移）。
STEP 2
消除重叠
调整这些位置，切成互不重叠的区间，避免一段代码被算进多个 tactic。
STEP 3
取代码片段
为每个区间抽出对应的源码片段。
STEP 4
收尾修正
处理空白、注释与特殊 tactic（have/let/calc/conv）。
它补上了 LeanREPL 的短板
产出的序列支持所有 Lean tactic，包括 LeanREPL 的 Tactic 模式不总能处理的 have、let、calc 模式与 conv 模式——这正是树搜索数据最容易丢失的部分。
▸调用示例 + 提取出的前两步（节选自原文 Appendix C.2）点开看 infotree="tactics" 如何还原成 goalsBefore / tactic / goalsAfter 
# 用 infotree="tactics" 取回原始证明轨迹，再解析成步骤

header, body = split_snippet(sample["formal_ground_truth"])

06 有意思的点

这是一篇务实的工程报告，几处设计取舍比 benchmark 数字更能说明它「为什么这么做」：

🔑用 header 当缓存 key
真正贵的是 import，那就只拿 import 当 key 复用 worker。
展开说明 ▸

验证一条证明，最贵的部分是加载库而非编译 body。把脚本拆成 header/body 后，只要 header（import 集合）相同就能复用已热身的 REPL——而 RL 训练里成千上万条证明往往共享同一行 import Mathlib，命中率极高。

启发：缓存的粒度要对准「最贵且最常重复」的那部分，而不是整段输入。

🧮一核一 REPL，还关掉超线程
单线程进程就该独占一个物理核，超线程反而添乱。
展开说明 ▸

Lean REPL 单线程、占用不超过一个核，所以每核常驻一个 REPL 是最自然的并行粒度。实验机还关闭了 SMT（超线程）——对这种 CPU 密集型任务，超线程会拖慢整体并带来不可预测的抖动。

启发：把并行单位对齐到硬件的真实并行度，比盲目开更多线程更稳。

🪶把复杂度藏进「一个函数」
并行、缓存、调度全在服务端，用户只见一个 check()。
展开说明 ▸

客户端只暴露一个 check()：传一批脚本、拿一批结构化结果。LRU 缓存、进程池、LRU 驱逐、排队重试这些复杂逻辑全部对调用者透明，极大降低「从 Python 调 Lean」的门槛。

启发：基础设施的价值，一半在性能，一半在「让别人能轻松用上这份性能」。

🧱直接用官方 REPL → 模块化可替换
不重造验证内核，因而天然兼容、易于替换。
展开说明 ▸

服务器直接构建在官方 LeanREPL 之上，所以兼容 REPL 支持的任何 Lean 版本。架构还是模块化的：只需小改进程派生（spawn）逻辑，就能换用别的 Lean 证明检查器，同时保留同一套 REST API。

启发：把「调度/缓存」与「验证内核」解耦，系统才有长期可维护性。

07 实验结论：一句话能说清

一句话：在 9,419 条 NuminaMath-LEAN 证明上，Kimina Lean Server 在 8/16/32/64 核全面快于 leanclient 与 LeanInteract（1.5–2×）；缓存单独再带来 1.94× 加速；吞吐随核心近线性扩展。 它已作为 Kimina-Prover 的核心验证引擎，支撑后者两度在 miniF2F 上登顶。

08 适用边界与一句话总结

这是一份目标明确的基础设施报告，它的适用性也很清晰：

  • 最适合：需要大批量、高频复用相同 import（如统一 import Mathlib）的大规模验证 / RL 训练 / 证明数据提取——这正是缓存命中率最高、收益最大的场景。
  • 受 REPL 能力约束：服务器直接用官方 LeanREPL，能力上限取决于 REPL；好处是兼容任何 REPL 支持的 Lean 版本，坏处是 REPL 本身的限制需在客户端（如 infotree 处理）绕过。
  • 架构可替换：只需小改进程派生逻辑，即可换用其它 Lean 证明检查器，同时保留同一套 REST API——对长期维护友好。
  • 缓存收益依赖 import 重复度：若每条证明的 import 都各不相同，header 缓存命中率下降，加速主要来自并行而非缓存。
这篇报告最值得记住的一句话
在「用形式化验证给模型做 RL」的时代，验证基础设施本身就是生产力：把最贵的库加载缓存起来、把多核吃满、再把调用收敛成一个 check()，就能让验证从训练瓶颈变成顺手的工具。
