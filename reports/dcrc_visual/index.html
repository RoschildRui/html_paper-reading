🎯 30 秒读懂

大模型在金融问答里很会「一本正经地算错数」。哪怕用 RAG 把财报喂进去，它仍然会三种翻车： 挑选错相似的噪声数字、用「概率猜词」假装算数、推理过程无法验证。

本文不去优化模型本身，而是换一条路——数据中心（data-centric）地训练一个「结构化智能体 DSA」， 把问答改造成「编译 + 执行」两段：DSA 像编译器一样挑证据、写出可执行程序（把不确定性关在这一步）， 再交给确定性的符号执行器去算（这一步 100% 可复现）。每一步都留下可审计的日志。

问题

为什么金融问答的数字幻觉这么难治？

想象用户问：「腾讯 2025 年归母净利润的增长率是多少？」 系统用 RAG 检索到一堆财报片段，里面既有正确事实，也混进了「长得很像但其实不对」的干扰项。 标准做法（RAG + LLM、或 CoT）会在三个地方接连失手——这正是论文用 Figure 1 讲清楚的故事。

🎯 挑战 1 · 噪声敏感
Noise Sensitivity（语义相近 vs 符号相异）
标准方法「净利润」和「归母净利润」嵌入太像，检索器把 NP=1850 也当成答案。
DCRC显式判别并 拒绝 概念漂移的干扰项，只接受精确匹配。
🧮 挑战 2 · 计算脆弱
Calculation Fragility（概率模仿 vs 确定执行）
标准方法下一 token 预测「假装」在算数，20% 被生成成「25%」。
DCRC把算式交给符号执行器，确定性计算、结果可复现。
🔍 挑战 3 · 可审计性危机
Auditability Crisis（似是而非 vs 透明验证）
标准方法CoT 悄悄丢弃证据，不说为什么，无法核查。
DCRC逐条记录 接受/拒绝 + 理由码，留下完整审计链。
核心观察：这三个问题是耦合的——单独修检索器或单独修生成器都不够。 论文因此主张：与其继续「模型中心」地打补丁，不如从数据入手，让模型学会「编译 + 执行」这一套可信流程。
已有方案

retriever-generator 框架卡在哪？

过去主流的金融数值推理都落在「检索器 → 生成器」两段式框架里，研究者各自优化其中一段。 但正因为两段是解耦的，无法统一应对上面三个挑战。下面挑三个代表性 SOTA 看它们各自做了什么、又卡在哪 （点开看方法与流程）。

APOLLOLREC-COLING'24
给检索器加「数字感知的负采样」，让它更会区分关键数值——但生成阶段仍是概率计算。
▶
文档→ 检索器（数字感知负采样） →生成器（概率计算）→答案

做了什么：针对「数值容易被忽略」的痛点，APOLLO 在训练检索器时引入 number-aware negative sampling， 构造数值上易混淆的负样本，让检索器学会挑出真正关键的数字事实。

卡在哪：它只优化了「找证据」这一段，找到证据后仍交给普通生成器做计算， 计算脆弱与可审计性问题原样保留。

ENCOREACL'24
通过「拆解答案公式」反推出可靠的推理过程来监督生成器——推理更可靠，但仍是文本生成。
▶
文档→检索→ 生成器（答案公式分解→可靠推理） →答案

做了什么：ENCORE 从标注的答案公式出发，分解出「可靠的推理过程」作为监督信号， 引导生成器学会更靠谱的多步推理链路。

卡在哪：它聚焦于优化生成器的推理质量，但计算本身依旧由语言模型「生成」， 缺乏确定性执行与对噪声证据的显式拒绝机制。

FINDEREMNLP'25
生成式检索做事实抽取 + 动态选 in-context 示例来增强 Program-of-Thought——本文最强对比基线。
▶
文档→ 生成式检索（事实抽取） →动态选示例→ PoT 提示生成程序→答案

做了什么：FINDER 用生成式检索器抽取事实，并动态挑选最相关的 in-context 例子来强化 Program-of-Thought 提示，从而生成可执行的计算程序。它是表现最强的前序方法（FinQA-Test 75.32%）。

卡在哪：它依赖提示工程而非训练出的判别能力，对「相似但不同」的噪声证据缺少显式拒绝， 也没有结构化的审计输出。本文 DSA-7B 在同等 7B 参数下把它再提升 9.34pp。

共同短板：这些方法都是「模型中心」——要么修检索、要么修生成， 把不确定的「算」和「判断证据」都留在了语言模型内部。本文的切入点恰恰相反：从数据出发， 训练一个会「编译」的智能体，把计算外包给确定性执行器。
本文方法 · 重头戏

DCRC：把问答变成「编译 + 执行」

DCRC（Data-centric Reasoning Compiler）训练一个 DSA（Data-centric Structuring Agent，数据中心结构化智能体）， 让它扮演「编译器」的角色。整体形式化为：

a = E(I),   I = π(q, D)

给定问题 q 和检索文档 D，DSA π 先把它们编译成一份可验证的中间表示 I； 再由确定性执行器 E 执行 I 得到答案 a。 中间表示 I 必须含三样东西：① 子任务拆解 T、② 带审计决策的证据池 P、③ 符号计算逻辑 L。

Phase 1 · 对抗数据构建：教模型「学会拒绝」

数据是 DCRC 的命门。光有正样本不够，关键是让模型见过足够刁钻的负样本。三步走：

  • ① 异构共识挖掘：用 K 个不同的强模型组成「教师委员会」，各自独立产出结构化 DSA；对每个候选值做硬投票，只有当多数（≥⌈K/2⌉）都「接受」且抽取的数值一致时，才纳入正样本集，消除单模型偏见与幻觉。
  • ② 硬负样本注入：基于正样本做受控扰动，模拟真实世界三类错误模式（见下方切换演示）。
  • ③ 一致性过滤：再用一个验证模型检查每条样本的 tag 与 why 是否语义自洽，不通过就丢弃。

三种硬负样本（以「腾讯 2025 归母净利润 = 1800」为正样本，点击切换）：

概念漂移 Concept Shift
时间错配 Temporal Mismatch
实体混淆 Entity Confusion

✅ 目标：腾讯 · 2025 · 归母净利润 = 1800ACCEPT [Exact_Match]
⚠️ 干扰：腾讯 · 2022 · 归母净利润 = 1500REJECT [Time_Mismatch]

指标类型对，但年份/期间不符。查 2025 的数据却混进了往年的值。

✅ 目标：腾讯 · 2025 · 归母净利润 = 1800ACCEPT [Exact_Match]
⚠️ 干扰：阿里巴巴 · 2025 · 归母净利润 = 1100REJECT [Entity_Mismatch]

指标和年份都对，但主体（公司/子公司 vs 集团）不符。

Phase 2 · 多阶段训练：先学格式，再学决策

Stage 1：结构感知 SFT（让关键 token「更重」）

普通 SFT 对每个 token 一视同仁。但 DSA 的灵魂是审计决策（Accept / Reject）。 于是论文对这些关键 token 的损失乘上权重 α = 2.0，逼模型把注意力放在「分类决策边界」上，而非流水账式的字段填充。

wt = 2.0  若  yt ∈ {Accept, Reject, tag, why}；  否则 wt = 1.0

Stage 2：GRPO 强化学习（五维奖励）

SFT 打好底子后，用 GRPO（组相对策略优化）进一步打磨决策质量。奖励由五个维度组成——注意其中有一个重罚项：

R_format
输出是否为合法、符合 schema 的 JSON（1 / 0）
R_retrieval
证据审计的 F1 分数，平衡精确率与召回率
R_exec
生成的计算逻辑能否被符号执行器跑通（1 / 0）
R_accuracy
执行结果与标准答案是否一致（误差 < ε）
R_consistency = −5
若某个被 Reject 的值竟然出现在最终公式里 → 重罚，杜绝「自相矛盾」
R_total = 五项之和

这个 −5 的一致性惩罚很巧妙：它直接用奖励信号封死了「嘴上说拒绝、手上却用了」这种最隐蔽的逻辑漏洞。

Phase 3 · 编译-执行推理：不确定性只留在编译阶段

训练好的 DSA 在推理时分工明确：编译这步可以「不确定」（用 LLM 挑证据、写程序），但执行这步必须「确定」。

① 编译：产出中间表示 I

  • 任务拆解 T：把复杂问题拆成原子子任务，每个含 target（目标指标）+ constraint（时间/条件）。
  • 共享证据池 P：每条证据带多头决策路由——同一个数字，在不同子任务视角下分别给出 Accept/Reject + 理由。
  • 符号逻辑 L：引用预注册算子库写出的计算表达式，如 subtract(1800,1500), divide(#0,1500)。

② 执行：确定性符号求值（三步）

  • 多头路由聚合：遍历证据池，按决策标签把证据分配到对应任务桶 Bi，同时生成审计日志。
  • 符号绑定 + 冲突检测：每个任务桶做一致性核验——恰好 1 个值则绑定，多个值则报 CONFLICT，0 个则报 MISSING。
  • 沙箱算子执行：只调用预注册算子库（add/subtract/.../table_avg），在安全沙箱里求值，彻底杜绝代码注入。

一个真实样例：PMI vs 标普 500 的五年回报差

几个有意思的点

为什么这套设计「优雅」？

① 「负向推理」：不仅说为什么对，还说为什么错

传统 CoT 只演示「如何得到正确答案」；DCRC 额外显式记录「为什么排除了那些错误选项」。 论文称之为 Negative Reasoning（负向推理）——审计逻辑准确率高达 99.6%， 拒绝理由几乎完美对齐预定义的错误分类（[Time_Mismatch]、[Entity_Mismatch] 等），而不是含糊的自由文本解释。

② 把不确定性「关进笼子」

整套方法的哲学可以一句话概括：

让语言模型的不确定性只停留在编译阶段（挑证据、写程序），而把执行阶段（数值计算）做成 100% 确定、可复现的符号求值。

这也解释了为什么即便完全不训练，光是改成「结构化编译」输出，1.5B 基座就能从 CoT 的 32.45% 升到 35.10%—— 结构化本身就在引导更精确的信息抽取。

③ 沙箱算子注册表：安全又确定

执行器只会调用预注册的函数（add / subtract / divide / table_avg ...），用 #N 引用前序步骤结果， 结果统一四舍五入到 5 位小数。好处有三：杜绝任意代码注入、支持多步引用、输出确定可复现。

查看算子注册表实现 （附录 C：10 个内置算子 + 设计原则） 
OPERATOR_REGISTRY = {
  "add":      lambda a,b: a + b,
  "subtract": lambda a,b: a - b,
  "multiply": lambda a,b: a * b,
  "divide":   lambda a,b: a / b,
  "exp":      lambda a,b: a ** b,
  "greater":  lambda a,b: "yes" if a > b else "no",
  "table_max": lambda row: max(row),
  "table_min": lambda row: min(row),
  "table_sum": lambda row: sum(row),
  "table_avg": lambda row: sum(row) / len(row),
}

结论：DCRC 用「对抗数据构建 + 多阶段训练 + 编译-执行推理」三段式，把标准大模型改造成可信的推理引擎， 系统性化解噪声敏感、计算脆弱与可审计性危机。论文展望未来扩展到多跳跨文档推理与实时流式金融数据。
