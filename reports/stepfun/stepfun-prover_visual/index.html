问题

为什么已有的证明器又慢又「笨」？

先理解痛点，才能理解本文为什么要让模型「一边思考一边验证」。

自动定理证明近年靠长思维链大模型取得了不小进展，但有一个尴尬的事实：它们要靠海量采样才能堆出好成绩。按已发表结果，把每题的采样次数从 32 次加到 64 次，准确率往往只多 3%～4%，呈明显的边际递减——这说明同一道题在多次尝试里反复栽在同样的错误模式上。

为什么会这样？因为这些证明器的推理模式是人为预先设定、僵化的，无法真正消化 Lean 4 给出的反馈。而一个熟练的 Lean 用户只需要几次尝试就能完成证明：他会读懂报错、诊断问题、自适应地换策略。这种巨大的效率差距，也成了普通用户使用证明器的门槛。于是作者提出了贯穿全文的问题：

「形式化证明器能否自我进化出合适的模式——去思考、去与验证器交互、并高效地推导出形式化证明？」

本文的回答是：放手让模型自己决定何时停止用工具，不限制它与 Lean 4 交互的次数，鼓励它进行开放式、工具辅助的推理——就像人类通过「试探、验证、反思」来学习和自我纠正一样。

已有方案

前人是怎么做的，又卡在哪

本文主要与两类范式形成对比。理解它们「把验证器放在哪里」，就能看懂本文的定位。点击卡片展开细节。

范式一

单步生成 + 树搜索

模型每次只生成一个证明步骤（tactic），再配合最佳优先搜索（BFS）或蒙特卡洛树搜索（MCTS）在证明树上探索路径。

状态→ LLM 出一步→ 树搜索挑分支↺ 回溯/扩展

卡在哪：搜索靠启发式导航，探索能力是用大量算力堆出来的；推理被切成孤立的小步，缺乏全局的自我反思。

范式二

整段证明生成 + 末端校验

模型一口气直接写出完整证明（如 DeepSeek-Prover、Kimina-Prover），验证器只在最后判一次对错，不参与中间推理。

题目→ LLM 写整段证明→ Lean 判对错✗→↺ 重新采样

卡在哪：反馈只用作最终的对错信号，中途没有任何修正机会；写错了只能整段重来，所以需要极大的采样量。

也有近期工作开始让模型与环境交互、增量改进证明，但本文指出它们往往「抽象掉了学习过程、限制了模型的自主性」——交互方式仍是预定义的。本文要做的，是仅凭测试时的环境反馈、无需额外监督，支撑模型自主用工具、迭代反思、自适应探索。

核心机制

工具集成推理：把验证器编织进思维链

这是全文最重要的一点——模型的一次「回答」不再是纯文本，而是文本推理、Lean 代码、真实反馈三者交错的混合轨迹。

在 rollout（生成）时，模型产出的内容由三种成分交替组成，并用特殊标记分隔：

  • 文本推理 g：用自然语言分析题目、解释报错、决定下一步怎么改。
  • Lean 草稿 <sketch>…</sketch>：包裹一段待验证的 Lean 4 代码。一旦检测到 </sketch>，生成暂停，代码被送进沙箱执行。
  • 环境反馈 <REPL>…</REPL>：沙箱（Lean4-REPL）的执行结果——成功信息或错误消息——被填回这对标记，喂给模型，生成继续。

最终得到一条混合轨迹 [g₁ ⊕ s₁ ⊕ f₁ ⊕ … ⊕ p]。当模型认为大功告成，它会生成特殊分隔符 </think> 并把最终的 Lean 证明放在其后——只对 </think> 之后的代码做基于规则的验证来给整条轨迹打分。这一「想清楚了再交卷」的设计，让奖励判定既可靠又简单。

本文方法

端到端训练流水线

如何把一个普通推理模型，训练成会「自主用工具、看反馈改证明」的证明器？下面这张图是全文的骨架。

流水线按训练阶段依次展开，点击每一阶段查看细节：

1
冷启动数据合成
先教会模型基本的「环境交互」姿势 · 含数据清洗
▸

作者汇集多个开源形式化数学数据集（Lean Workbook、STP 数据集），并用 Kimina-Autoformalizer-7B 把 Numina Math 1.5 的部分题目自动形式化。但这些题目有反复出现的质量问题：

  • 同义反复：结论从前提平凡可得，没有真正的推理。
  • 前提矛盾：题目本身不可解或逻辑不自洽。
  • 结论无关：要证的命题与前提没有实质联系。
  • 平凡或病态：缺乏数学深度、结构不良。

于是用 DeepSeek-V3 过滤掉低质量题目，再用两条并行流程构造冷启动数据集 𝒟₀：

  • 多轮数据：用 Claude Sonnet 4 收集约 8,000 条有效的多轮轨迹，作为初始的多轮推理数据。
  • 单轮数据：把 Kimina-Prover-72B 生成的证明去掉中间 tactic 块和其间的推理，只保留题目的自然语言推理和最终 Lean 4 答案——因为作者发现最终答案有时与中间步骤的逻辑并不吻合，说明中间推理未必必要。
2
两阶段监督微调（SFT）
先学 Lean 语法，再学工具集成推理 → 得到 ℳ₀
▸
  • 第一阶段：用开源 STP 数据集的问答对微调起点模型，建立对 Lean 4 语法和证明结构的基本理解。
  • 第二阶段：用冷启动数据集 𝒟₀ 继续微调，建立初步的工具集成推理与证明生成能力。

两阶段后得到冷启动模型 ℳ₀。基座模型为 DeepSeek-R1-Distill-Qwen-7B / 32B。

一个细节：训练时对 <REPL>…</REPL> 区间的反馈 token 做 loss 掩码（不计入损失）。这样外部反馈 token 不会干扰损失计算，既保证训练稳定，又保护模型自身生成的连贯推理不被打断。

3
响应模式融合（Response Patterns Fusion）
解决 ℳ₀ 风格「水土不服」的问题 → 得到 ℳ₁
▸

ℳ₀ 虽有基本交互能力，但表现远低于预期。分析发现一个关键症结：ℳ₀ 难以把 Claude 风格和 Kimina 风格这两种不同的响应模式融合好。作者用一个巧妙的方法解决：

  • 收集错误响应：先收集 Kimina-Prover-72B 生成的错误响应。
  • 纠错并建库：用 ℳ₀ 系统性地修正这些错误响应、同时保留有效的推理轨迹，得到精炼数据集 𝒟₁。
  • 增强模型：仅用 𝒟₁ 在起点模型上做 SFT，得到改进模型 ℳ₁——它把不同风格的响应「调和」到了一起，作为后续强化学习的起点。
4
工具集成强化学习（GRPO）
二元结果奖励 · 无 KL 正则 · 在 rollout 中调用沙箱
▸

与只生成纯文本的常规 RL 不同，这里的 rollout 让 LLM 与沙箱式环境协同工作，产出文本 + Lean 代码 + 实时反馈的混合内容（即前面「核心机制」一节描述的循环）。

奖励设计：只看 </think> 之后的最终证明——通过 REPL 验证则奖励为 1，否则为 0。这种二元结果奖励简化了监督、抑制 reward hacking，并因为只盯最终结果而鼓励更多样的解题行为。

算法：在 ℳ₁ 上用 GRPO 训练；仿照「PPO 去掉 KL 正则」的做法，这里也省去 KL 项，以鼓励从一个已对齐的指令模型出发去探索。每题采样 G 个候选，按组内奖励做标准化得到优势：

Aᵢ = ( rᵢ − mean(r₁,…,r_G) ) / std(r₁,…,r_G)

再以 PPO 式的裁剪目标（clip，无 KL）优化策略。

5
RL-SFT 迭代循环
用 RL 筛出的优质轨迹再做 SFT，再 RL
▸

当工具集成 RL 收敛后，作者从训练中准确率低于 0.5 的难题里收集正确轨迹，再筛出那些展现了充分 REPL 反馈分析的轨迹。这些精选轨迹用于再做一轮 SFT，随后再进行二次强化学习，进一步增强模型的工具集成推理能力。这就是图 2 中「More SFT data from RL」那条回环。

6
训练细节与基础设施
动态数据筛选 · Lean4-REPL 远程服务 · 10× 提速
▸

RL 关键参数：rollout batch = 512，每题 8 个样本，最大生成长度 16384，REPL 超时 60 秒，温度 1.0、top-p 0.999（鼓励探索）。

动态数据筛选（亮点）：训练提示来自 STP 数据集，先剔除 SFT 用过的题。作者不在训练前静态筛数据，而是把数据选择嵌进 RL 训练循环本身：用单轮 RL 跑出每题的成功率，只保留成功率严格介于 0 和 1 之间的题——既去掉永远做对的「太简单」题，也去掉当前永远做不出的「太难」题。这种在训练中动态筛选的策略，能抓住那些「起初太难、但随模型变强而变得可解」的高价值题目。

Lean 4 服务工程（让多轮 RL 可行的关键）：

  • 改造 Lean4-REPL 主函数，优化内存回收，减少因重复调用导致的内存爆炸和 REPL 重启（该改动已被官方开发者采纳，见 PR #83）。
  • 归类 REPL 所有可能的返回类型并逐一处理，提升大模型–REPL 交互的稳定性；设 60 秒超时，防止模型滥用搜索式 tactic。
  • 对 LLM 多轮输入流和证明草稿提交都做异步处理，消除样本间生成/验证耗时差异带来的延迟。
  • 用 Redis 作为消息中枢搭建「生产者–中枢–消费者」式的 Lean4-REPL 远程服务，可并发运行 1000+ 个 Lean4-REPL 进程，并把训练与服务的不稳定隔离开。

这些优化让多轮 RL 训练提速 10 倍以上，并使「不限交互次数」的多轮 RL 在工程上真正可行。

实例演示

跟着模型走一遍：6 轮试错证完一道不等式

这是论文附录给出的真实轨迹。点「下一步」，看模型如何从一句报错，一步步逼近正确证明——这正是「一边思考一边验证」的精髓。

待证题目（正实数 x, y, z）
theorem (x y z : ℝ) (hx : 0 < x) (hy : 0 < y) (hz : 0 < z) : (x^2 - z^2)/(y+z) + (y^2 - x^2)/(z+x) + (z^2 - y^2)/(x+y) ≥ 0 := by
第 1 轮 · 先交个白卷试试水报错
模型先做了大量代数分析（通分、平方差、对称性观察……），然后只把定理头交给 Lean，连证明体都没写，纯粹想看看环境会回什么。
<sketch>
theorem test_theorem (x y z : ℝ) (hx : 0 < x) (hy : 0 < y) (hz : 0 < z) :
  (x^2 - z^2)/(y+z) + (y^2 - x^2)/(z+x) + (z^2 - y^2)/(x+y) ≥ 0 := by
<REPL> 反馈
error: unexpected end of input; expected '{'
error: unsolved goals
  ⊢ (x^2 - z^2)/(y+z) + (y^2 - x^2)/(z+x) + (z^2 - y^2)/(x+y) ≥ 0
💡 学到：光有定理头不行，缺证明体（目标尚未解决）。下一步得真正动手写策略。
第 2 轮 · 通分 + 暴力凑平方报错
模型决定清分母：把三项通分成「分子 / 分母」，用 div_nonneg 拆成「分子≥0」「分母>0」两个子目标，分子用 nlinarith + 一堆 sq_nonneg 平方项硬凑，分母用 mul_pos。
<sketch>（关键片段）
  have h1 : (y+z) > 0 := add_pos hy hz   -- 同理 h2, h3
  have h4 : … = (分子)/((y+z)*(z+x)*(x+y)) := by
    field_simp [h1.ne.symm, h2.ne.symm, h3.ne.symm]; ring
  rw [h4]
  apply div_nonneg
  · ring_nf
    nlinarith [sq_nonneg (x-y), sq_nonneg (y-z), sq_nonneg (z-x), …]
  · apply mul_pos; apply mul_pos; all_goals linarith
<REPL> 反馈
error: linarith failed to find a contradiction
  a✝ : 0 > -(x^2*z^2) - x^2*y^2 + (x^4 - z^2*y^2) + z^4 + y^4 ⊢ False
error: 'apply' failed, failed to unify  0 < ?a * ?b
  with  0 ≤ (y+z)*(z+x)*(x+y)
💡 学到：两处都崩了——(1) 乱凑的平方项证不出分子；(2) mul_pos 给的是 0 < …，可目标是 0 ≤ …，类型对不上。但报错里泄露了分子化简后的真实样子。
第 3 轮 · 用 ring_nf 看清分子真容报错
模型抓住上一轮报错里的线索，先用 ring_nf 把分子展开、再用 sorry 占位，专门看看分子化简成了什么。
<REPL> 反馈（关键：暴露了分子的标准形）
sorry 处目标:
  ⊢ 0 ≤ -(x^2*z^2) - x^2*y^2 + (x^4 - z^2*y^2) + z^4 + y^4
（即  x⁴ + y⁴ + z⁴ - x²y² - x²z² - y²z²）
error: 'apply mul_pos' 仍无法匹配 0 ≤ (y+z)*(z+x)*(x+y)
💡 关键发现：分子其实就是 x⁴+y⁴+z⁴ - x²y² - x²z² - y²z²——这是个经典可写成平方和的式子！方向有了。
第 4 轮 · 平方和！分子搞定报错
模型识别出 x⁴+y⁴+z⁴-x²y²-x²z²-y²z² = ½·((x²-y²)²+(y²-z²)²+(z²-x²)²)，是三个平方的和，必然非负。于是用 num_eq、sqForm 重写，再用 mul_nonneg + sq_nonneg 收掉分子。
<sketch>（分子部分）
    have num_eq : (分子) = x^4+y^4+z^4 - x^2*y^2 - x^2*z^2 - y^2*z^2 := by ring
    rw [num_eq]
    have sqForm : … = (1/2)*((x^2-y^2)^2 + (y^2-z^2)^2 + (z^2-x^2)^2) := by ring
    rw [sqForm]
    apply mul_nonneg
    · norm_num
    · apply add_nonneg; … exact sq_nonneg (x^2-y^2) …   -- 三个平方非负
<REPL> 反馈
error: 'apply mul_pos' failed, failed to unify  0 < ?a * ?b
  with  0 ≤ (y+z)*(z+x)*(x+y)   （分子已过，只剩分母这个小尾巴）
💡 学到：分子彻底证完！只剩分母——而分母还是卡在同一个 0 ≤ vs 0 < 的类型问题上。
第 5 轮 · 又试了一次分母，仍不对报错
模型加了注释「分母三个因子都正、积必正」，但分母证法没变，还是 apply mul_pos; apply mul_pos; all_goals linarith——本质问题没解决。
<REPL> 反馈
error: 'apply' failed, failed to unify  0 < ?a * ?b
  with  0 ≤ (y+z)*(z+x)*(x+y)
💡 学到：同样的错再现一次，说明 mul_pos 这条路对 0 ≤ 的目标根本走不通——必须换个思路：先证「>0」，再转成「≥0」。
第 6 轮 · 用 le_of_lt 收尾通过 ✓
模型改用：先 mul_pos 得到分母严格大于 0（pos2 : 0 < …），再用 le_of_lt 把「>0」转成目标要的「≥0」。
<sketch>（分母部分）
  · have pos1 : 0 < (y+z)*(z+x) := mul_pos h1 h2
    have pos2 : 0 < (y+z)*(z+x)*(x+y) := mul_pos pos1 h3
    exact le_of_lt pos2
<REPL> 反馈
{}   ← 空消息 = 零报错 = 证明完整且正确 ✓
💡 成功：REPL 返回空，说明全部目标都被证完。模型随即生成 </think>，把这份干净的完整证明作为最终答案交卷。
这条轨迹妙在哪：模型并不是一开始就知道「分子是平方和、分母要用 le_of_lt」——这两个关键洞察都是被 Lean 的真实报错逼出来的。第 3 轮的 ring_nf 反馈暴露了分子的标准形，第 5 轮反复撞墙才意识到要换分母证法。没有中途的验证反馈，纯靠一次性生成几乎不可能命中。

给模型更多「思考 + 交互」的空间，准确率单调上升——更多的工具交互就是它的测试时算力。RL 阶段训练奖励也从约 0.63 稳步升到 0.78，测试 pass@1 同步抬升，说明 RL 持续生效。

RL 还「涌现」出了哪些行为？

通过工具集成 RL（带冷启动），StepFun-Prover 发展出若干会利用实时反馈的高级行为，包括但不限于：

主动消除警告

即便 REPL 没报错、只有 warning，模型也会主动把警告处理干净，而不是见好就收。

超时即重构

当某段执行超过时间阈值（如 60 秒），模型会动态重构证明，换一条更省时的路径。

迭代式自我改进

通过分析 REPL 反馈逐轮改进解答——正是上面实例演示展现的能力。

结论与展望

把「人类式反思 + 形式化验证」结合起来

本文提出了一条端到端训练工具集成推理模型的流水线，核心是冷启动数据合成与工具集成强化学习。由此得到的 StepFun-Prover-Preview，靠在推理中持续利用实时环境反馈来迭代精修证明，在 miniF2F-test 上用极少采样达到 70.0% pass@1，证明了「人类式反思 + 形式化验证」结合的有效性。
