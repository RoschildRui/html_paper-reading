TL;DR

30 秒看懂

Transformer 用的 softmax 注意力计算量随序列长度平方级增长，是上下文窗口难以变长的根本瓶颈。MiniMax 把绝大多数层换成 Lightning Attention（一种 I/O 感知、真正线性复杂度的线性注意力），再用 MoE 把参数堆到 4560 亿。

关键设计是一种混合架构：每 7 层 Lightning Attention 之后插 1 层 softmax 注意力，既拿到线性的速度，又补回线性注意力欠缺的检索能力。结果：训练时支持 100 万 token 上下文、推理可外推到 400 万 token，而综合性能对标 GPT-4o 与 Claude-3.5-Sonnet。

配套还重写了整套训练/推理框架（LASP+、Varlen Ring Attention、EP/ETP 通信重叠、定制 CUDA kernel），端到端 MFU 超过 75%。模型权重已开源：github.com/MiniMax-AI/MiniMax-01 ↗。

问题定义

为什么上下文窗口卡住了

过去两年上下文窗口能变长，主要靠更强的 GPU 和更好的 I/O 感知 softmax 注意力实现（如 FlashAttention）。但大多数模型仍停在 32K–256K，再往上越来越难——因为 Transformer 的注意力是平方复杂度：序列翻倍，计算量变四倍，增速远超硬件进步。

而现实需求往往超出这个范围：把一整本专业书当上下文、给模型整个代码工程、用成百上千示例做 in-context learning，都需要远更长的窗口。学界为降复杂度提出过稀疏注意力、线性注意力、长卷积、状态空间模型（Mamba）、线性 RNN 等方案，理论上都很美——

但它们有一个共同尴尬：

Despite their theoretical promise, these innovations have seen limited adoption in commercial-scale models. 尽管理论上前景可观，这些创新在商用规模的模型里几乎没被采用过。

本文的目标，就是第一次把线性注意力真正用到数千亿参数的旗舰模型上，在不牺牲性能的前提下，把上下文窗口拉长一个数量级。这要求同时平衡好三件事：网络架构、数据、计算。

已有方案速览

三类注意力，各卡在哪

为理解 MiniMax 的取舍，先看与它直接形成对比的三条路线。点击展开看每种「做了什么、怎么做、卡在哪」。

① Softmax 注意力（标准 Transformer） Vaswani et al., NeurIPS 2017
检索能力强、是事实标准，但计算/显存随长度平方增长，长上下文太贵。
▸

做了什么：对每个 query，计算它与所有 key 的相似度 Softmax(QKᵀ/√d)·V，得到一张 n×n 的注意力矩阵。它能精确地「回看」全部历史 token，因此检索/in-context learning 能力极强，是当今几乎所有顶级模型的基座。

卡在哪：那张 n×n 矩阵就是诅咒——计算与显存都是 O(n²)。序列从 100K 到 1M，注意力开销涨 100 倍。FlashAttention 这类 I/O 感知实现只能把常数项压下来，改变不了平方这个量级。所以窗口再往上走，硬件根本追不上。

与本文关系：MiniMax 没有完全抛弃它——而是把它当成「检索专用层」，每 8 层只保留 1 层 softmax 注意力来补检索短板。

② 线性注意力（右乘核技巧 / TransNormer） Qin et al., 2022
用结合律把复杂度降到线性 O(n)，但 causal 场景要算 cumsum、不可并行，且检索弱。
▸

做了什么：去掉 softmax 后，注意力变成纯矩阵乘 (QKᵀ)V。利用矩阵乘法结合律改成 Q(KᵀV)——先算 KᵀV 得到一个只有 d×d 的小矩阵（与序列长度无关），复杂度从 O(n²d) 降到 O(nd²)，对长序列就是线性。

卡在哪：在因果语言建模（每个 token 只能看前面）下，右乘的优势被破坏，必须沿序列做 cumsum（前缀和）累积 KᵀV 状态。这个 cumsum 串行、无法高效并行，在 GPU 上慢——这也是为什么这个九年前就被提出的机制，至今 LLaMA3、Qwen2.5、DeepSeek-V3、Mistral 都没用它。

与本文关系：Lightning Attention 正是这条路线的「工程化升级版」——用分块（tiling）绕开 cumsum，是 MiniMax 架构的主力层。

③ 状态空间模型 / 线性 RNN（Mamba 系等） Gu & Dao, 2023–2024
同样把序列建模做成线性递推，但纯线性模型普遍检索受限，未在商用规模验证。
▸

做了什么：把序列建模写成一个随时间更新的固定大小隐藏状态的递推过程（SSM / 线性 RNN），推理时每步只更新状态、不重算整段历史，因此天然线性、显存恒定。

卡在哪：和纯线性注意力同病相怜——固定状态容量有限，检索能力弱。本文实验也复现了这一点：纯线性模型在语言建模上接近 Transformer，但在 NIAH（大海捞针）这类检索任务上明显落后，不适合直接做 LLM。同时它们也没有在数千亿参数规模被验证过。

与本文关系：作者对比了 hybrid-cosformer2、hybrid-hgrn2、滑动窗口注意力等多种混合变体，最终 hybrid-lightning 全面胜出，成为最终选择。

混合架构 + Lightning Attention + MoE

图 1（自制示意图，忠于原文 Figure 3）：MiniMax-Text-01 的混合架构——每 7 层 Lightning Attention 后接 1 层 Softmax Attention，共 80 层；每层的 feature mixer 都是 MoE。 展开说明 ▸
  • 纵向 = 数据流：token 序列从顶部进入，自下而上穿过 80 层，每层先过 channel mixer（注意力，做 token 之间的混合），再过 feature mixer（MoE，做特征维度的混合），最后输出预测下一个 token。
  • 浅黄块 = Lightning Attention：架构主力，占每组 8 层中的前 7 层。负责线性复杂度的高效长序列建模，是速度与显存优势的来源。
  • 绿色块 = Softmax Attention：每组的第 8 层。配 Group Query Attention（组大小 8）和只施加在一半维度上的 RoPE，专门补回线性层欠缺的精确检索与长度外推能力。
  • 橙色块 = MoE feature mixer：每层都有，32 个专家、top-2 路由，每 token 只激活其中 2 个，使总参数可达 456B 但单 token 仅激活 45.9B。
  • 虚线框「×10 组」：这 8 层为一个重复单元，叠 10 次得到 80 层；7:1 的线性/softmax 配比是大量小规模实验扫出来的最佳混合比例。
一句话：用大量便宜的线性层扛长度，少量贵的 softmax 层守检索，再用 MoE 把容量堆上去——这就是 MiniMax-01 的骨架。

① Lightning Attention：用分块绕开 cumsum

线性注意力在因果场景下慢，根源是那个串行的 cumsum。Lightning Attention 的关键 trick 是分块（tiling）：把注意力计算拆成「块内（intra-block）」和「块间（inter-block）」两部分，分别用左乘和右乘，从而既保持线性、又能在 GPU 上高效并行（I/O 感知，类比 FlashAttention）。

图 2（自制示意图，忠于原文 Algorithm 1 / Figure 5）：Lightning Attention 的块内 + 块间分解——对角块用左乘，其余靠一个不断累积的 KV 状态做右乘。 展开说明 ▸
  • 左侧网格 = 注意力矩阵被切成块：Q、K、V 沿序列维度切成大小 B×d 的小块。橙色对角块是「块内」，绿色下三角块是「块间」，右上灰块因果掩码置零（当前 token 看不到未来）。
  • 橙色块内（左乘）：在每个对角块内部直接算 [(QₜKₜᵀ)⊙M]Vₜ。块很小，所以这部分平方开销可忽略，且能并行；掩码 M 保证因果性。
  • 绿色块间（右乘）：当前块与所有历史块的交互，不逐块重算，而是直接乘上一个累积好的 KV 状态：Qₜ·(KV)。这一步是线性复杂度的关键。
  • 底部 KV 状态（递推）：每处理完一块就更新 KV ← KV + KₜᵀVₜ，把历史信息压进一个固定大小的 d×d 状态里向后传递——这就替代了原来串行的 cumsum。
  • I/O 感知：整个过程把 Q/K/V 分块从显存（HBM）搬到片上 SRAM 计算，减少访存，最终复杂度 O(nd² + nBd)，对长序列即线性。
一句话：对角块「精算」、块间用累积状态「估算」，把不可并行的前缀和换成可并行的分块矩阵乘，这才让线性注意力在 GPU 上真正快起来。

② 线性的本质：换个乘法顺序

为什么线性注意力能省这么多？核心只是一个矩阵乘法结合律。下面对比同一个计算的两种算法。

softmax / 左乘
O = (Q·Kᵀ)·V
先得 n×n 矩阵
O(n²·d)
随序列长度平方增长
线性 / 右乘
O = Q·(Kᵀ·V)
先得 d×d 小状态
O(n·d²)
d≪n 时即线性
图 3（自制示意图，忠于原文 Eq. 2–3 / Figure 5）：线性注意力的「右乘核技巧」——先算 KᵀV 把维度压到 d×d，避开 n×n 注意力矩阵。 展开说明 ▸
  • 左面板（左乘，贵）：先算 QKᵀ 得到 n×n 的完整注意力矩阵，再乘 V。开销 O(n²d)，序列越长越吃不消，是 softmax 的固有形态。
  • 右面板（右乘，省）：去掉 softmax 后可改变乘法顺序：先算 KᵀV，得到与序列长度无关的 d×d 小矩阵，再左乘 Q。开销 O(nd²)，因 d≪n 故为线性。
  • 代价是什么：这个等价只在非因果下成立；因果建模下需要逐位置累积 KᵀV（即图 2 里的 KV 状态），Lightning Attention 的分块正是为高效完成这一步而生。
一句话：softmax 的非线性逼你显式构造 n×n 矩阵；去掉它，乘法结合律就能把成本从「平方」变「线性」。

③ MoE：用稀疏激活把容量堆上去

feature mixer 用 Mixture of Experts 替换普通 FFN：每层 32 个专家，门控只把每个 token 路由给得分最高的 2 个专家（top-2）。于是总参数能堆到 456B，但单 token 实际只激活 45.9B，算力与显存可控。

  • 路由坍缩问题：规模变大时 token 容易扎堆涌向少数专家（routing collapse），导致负载失衡、训练不稳。
  • Global Router：在 GShard 辅助损失基础上加一步跨 EP 组的 allgather，先全局同步各专家待处理 token 数再分发，显著降低 token drop 率、稳住训练。
  • token-drop 策略：给每个专家设容量上限，超出即丢弃，换取训练效率。

④ 工程：让百万 token 真的跑得动

现有分布式框架几乎都是为 softmax 注意力设计的。这套「Lightning + Softmax + MoE」的新架构，逼着作者把训练/推理框架整个重写。点击下方了解关键工程优化。

四项核心工程优化 （MoE 通信重叠、Varlen Ring Attention、LASP+、Lightning 推理 kernel）
  • EP / ETP 通信重叠：MoE 的 all-to-all 通信用 Expert Parallel + 新引入的 Expert Tensor Parallel 切分专家权重，并让通信与不同专家组的计算重叠，纯通信开销较优化前降低 50%。
  • Varlen Ring Attention：针对「data-packing」（多个不等长样本首尾拼接）的 softmax 长序列场景，直接在整条拼接序列上做 ring attention，避免传统实现因要求长度整除而产生的大量 padding 浪费。
  • LASP+（改进的线性注意力序列并行）：原版 LASP 各 CP rank 需串行 send-recv 交换 KV 块、互相依赖。LASP+ 先各自算局部前缀和、再 AllGather 同步，把串行变并行，速度最高提升到原来的 1/T（T 为节点数）。
  • Lightning 推理 kernel：批量 kernel 融合、prefill 与 decode 分离执行、多级 padding（32/64/128/256）、StridedBatchedMatmul 扩展，端到端 MFU 在 H20 上 >75%。

长上下文还用三阶段训练逐步把窗口扩到 1M：每阶段上采样不同长度区间的长文本、调高 RoPE base 频率，并在每阶段后 20% 混入 10% 高质量长文本问答数据，靠源权重线性插值平滑过渡、稳住训练。

为何有效

反直觉：混合架构的检索甚至超过纯 softmax

常识会觉得「掺了线性层，检索肯定打折」。但实验发现 hybrid-lightning 在检索（NIAH）和长度外推上不仅追平、还超过纯 softmax。作者给出的解释很漂亮——把两种注意力都写成线性递推来比「容量」。

softmax attention 可被理解为一种线性 RNN：每个时间步都从头重算隐藏状态，像是「Going Through a Book」——反复重读全部历史来精确保留信息。 而线性注意力没有这个重算过程，所以单看检索它更弱；但它的「记忆状态」更大。

把 RNN 的容量定义为其循环状态的大小：

Softmax 注意力

状态容量 ≈ O(d)

逐步重算、检索精确，但单步可携带的「记忆」维度有限。

Lightning 注意力

状态容量 ≈ O(d²/h)

那个 d×d 的 KV 状态本身就是一块大记忆；因 d > h，容量比 softmax 更大。

于是 hybrid 把两者长处叠加：softmax 层提供精确重读、lightning 层提供大容量记忆，合起来检索与外推都更强。这也解释了为什么纯线性模型不行、而混合模型行——少量 softmax 层是不可省的「检索锚点」。

有意思的点

几个值得记住的设计取舍

  • 训练 1M，外推到 4M：得益于架构的长度外推能力，模型只在 ≤1M 上训练，却能在 400 万 token 的大海捞针（NIAH）压力测试中通过——成本可控地把推理窗口又拉长 4 倍。
  • PostNorm（DeepNorm）打败 PreNorm：主流 LLM 多用 PreNorm 求稳，但它会因梯度走捷径而降低「有效深度」。在这个对深度敏感的深层混合架构里，配 DeepNorm 的 PostNorm 反而在所有指标上更好。
  • 推理时 softmax 才是大头：在 1,024,000 token 长度下，softmax 注意力占了约 95% 的注意力延迟，而 lightning 实现只占 不到 12%——直观印证了「把大多数层换成线性」的价值。
  • 单机可部署是硬约束：总参数特意压在 500B 以内，确保用 8×80G GPU + 8bit 量化能在单节点上跑 1M token 推理，省掉跨机通信。
  • RoPE 只加一半维度：softmax 层只对一半注意力头维度施加 RoPE，就能实现长度外推而不掉点。

性能对标顶级闭源，长上下文显著领先
